# hold_aruco — удержание дрона над ArUco-меткой

Тестовая программа для Обрика (ROS 2 Humble, `sverk_interfaces`). Взлетает,
цепляется за ближайшую видимую метку, держится над ней `HOLD_S` секунд и садится.

Это **не** часть зачётного решения: ни миссий, ни карты поля, ни роя, ни LLM.
Это стенд, на котором в первый день на площадке проверяется всё спорное про
железо — за один полёт и без риска потерять попытку.

```
hold_aruco.py     единственный исполняемый файл, ~450 строк
requirements.txt  opencv-python, numpy (sverk_interfaces есть только на борту)
```

## Что этим полётом проверяется

| Гипотеза | Где смотреть в логе |
|---|---|
| Патч `yuv422_yuy2` работает | вообще есть строки с меткой, а не `кадр не получен` |
| `MARKER_M` = 0.25 м — правда | `h≈` совпадает с реальной высотой по рулетке |
| Знак осей `body` не перепутан | сдвинули дрон рукой — команда идёт **навстречу** |
| `navigate(z=0)` уводит высоту вверх | `h≈` без поправок ползла бы; здесь её держит `hold_alt` |
| `land()` действительно сажает | `ПОСАДКА: дрон на земле`, а не `снижения не видно` |
| Дрон не выпадает из OFFBOARD | нет строк `navigate отказал` |

## Как это работает

Телеметрия не используется вообще — `get_telemetry` на нашей сборке виснет без
FCU (`docs/zmeyka.md`). Всё читается с самой метки:

- **где мы** — смещение метки от центра кадра, переведённое в метры масштабом
  `MARKER_M / сторона_в_пикселях`. Камера смотрит вниз, поэтому верх кадра = «вперёд»,
  левый край = «влево», а двигаться надо навстречу смещению метки;
- **высота** — сторона метки в пикселях обратно пропорциональна высоте. Эталон
  (`SIDE_REF`) снимается один раз после взлёта на спокойном кадре;
- **курс** — поворот метки в кадре. Эталон (`ANGLE_REF`) снимается там же.

Калибровка камеры и `camera_info` не нужны: масштаб берётся с метки, а не с высоты.

Регулятор пропорциональный, `GAIN = 0.7` — отрабатывается не весь промах разом,
иначе дрон проскакивает цель и раскачивается. Мёртвая зона `TOL_M = 0.10` задана
в метрах, а не в долях кадра как в «Змейке»: там допуск означал «попал в узел
маршрута», здесь — «висит над меткой», и 0.08 диагонали кадра дали бы на рабочей
высоте 24 см свободного дрейфа.

Метка одна на весь полёт. Перецепляться на соседнюю нельзя: между метками поля
2,4 м, и дрон запрыгал бы между ними. Пропала своя — кадр считается слепым, даже
если в нём видны чужие; два слепых подряд → подъём на 0,3 м осмотреться (суммарно
не выше +1 м над рабочей высотой, п. 2.6.3 регламента — потолок 4 м); 20 слепых
подряд → посадка.

## Настройки

Правится **только** блок `НАСТРОЙКИ` в начале файла. Что трогают на площадке:

| Константа | Значение | Когда менять |
|---|---|---|
| `MARKER_M` | 0.25 | **обязательно перемерить рулеткой** — см. ниже |
| `ALT` | 1.5 | 0.7 на первый проверочный взлёт |
| `HOLD_S` | 60.0 | 15 на первый проверочный взлёт |
| `GAIN` | 0.7 | дрон раскачивается — уменьшить до 0.4–0.5 |
| `HOP_PAD` | 0.8 | дрон дёргается / снимок на ходу — увеличить |
| `TOL_M` | 0.10 | дрон постоянно подруливает по мелочи — увеличить |

## Запуск

Локально (на этой машине `sverk_interfaces` нет — только синтаксис):

```bash
python3 -m py_compile hold_aruco.py
```

На борту. `ssh sverk@<IP>`, пароль `sverk` — попадаете сразу внутрь контейнера
`sverk_ros2` (порт 2222 — это хост, туда не надо):

```bash
scp -r hold_aruco sverk@<IP>:~/
ssh sverk@<IP>
~/hold_aruco/hold_aruco.py 2>&1 | tee ~/log_hold.txt
```

Один файл, без обёрток. Шебанг указывает на `~/venv_fly/bin/python3` — отдельное
окружение, см. ниже. Если шебанг почему-то не сработал («bad interpreter»), то же
самое явно:

```bash
~/venv_fly/bin/python3 ~/hold_aruco/hold_aruco.py
```

### Зачем отдельное окружение

На борту через pip поставлен numpy 2.2.6 поверх системного 1.21.5, а
`python3-opencv` (4.5.4) собран под numpy 1.x. С двойкой `import cv2` падает:

```
ImportError: numpy.core.multiarray failed to import
```

Ломается не только эта программа — `sverk_interfaces` тоже импортирует `cv2`,
то есть весь Python-API платформы. Систему решено не трогать: numpy 2 нужен
чужому коду на том же борте (`pid-tuning-assistant`). Окружение создано так:

```bash
python3 -m venv --system-site-packages ~/venv_fly
~/venv_fly/bin/pip install "numpy<2"
```

`--system-site-packages` обязателен: `rclpy` и `cv2` берутся из системы, поставить
их через pip нельзя — `rclpy` часть ROS-сборки. numpy 1.26.4 из venv имеет
приоритет над `/usr/local` с двойкой, а cv2 4.5.4, собранный под 1.21, с 1.26
совместим по ABI — проверено на борту.

Ставить в это окружение numpy 2 бессмысленно: сломается ровно так же. Дело не в
том, какой numpy установлен, а в том, подо что скомпилирован бинарник OpenCV.

Окружение ROS (`LD_LIBRARY_PATH` и прочее) приходит из `~/.bashrc`, который
сорсит `setup.bash`. Работает это только в **интерактивной** сессии: в
`ssh <host> "команда"` `.bashrc` не отрабатывает, там надо сорсить руками.

Предполётная проверка — `selfcheck`, но **сначала надо поднять саму ноду**, в
автозапуске её нет (иначе CLI ругается «action /self_check/run недоступен»):

```bash
source /opt/ros/*/setup.bash && source ~/sverk_ws/install/setup.bash
ros2 run self_check self_check_node &        # нода
ros2 run self_check selfcheck                # сам отчёт (не selfcheck.py)
```

Критично зелёное: `power_battery`, `camera_stream`, `vpe_consistency`,
`aruco_pipeline`.

Терминал должен быть виден — вывод читают судьи, в фон (`&`) не уводить.
Ctrl+C — штатный останов: посадка идёт тем же путём, через `finally`.

## Порядок первого прогона

1. **Без взлёта.** Положить дрон прямо на метку, камерой вниз. Убедиться, что id
   читается:
   ```python
   import sverk_interfaces, hold_aruco
   d = sverk_interfaces.init(Nodename="check"); hold_aruco.patch_yuv(d)
   print(hold_aruco.markers(hold_aruco.look(d)))
   ```
   Пусто — дальше не идти: либо камера, либо словарь, либо ракурс.
2. **Перемерить метку рулеткой** и вписать в `MARKER_M`. Значение 0.25 взято из
   `docs/field-map/map.txt`, а та карта на железе ещё не сверялась. Ошибка здесь
   даёт систематический промах и «плавающую» высоту.
3. **Короткий взлёт:** `ALT = 0.7`, `HOLD_S = 15`, руки на пульте. Сверить в логе
   `h≈` с рулеткой; сдвинуть дрон рукой и проверить, что команда идёт навстречу
   сдвигу (если от — перепутан знак Y, `docs/openclaw/03-zhelezo-api-i-boevye-grabli.md`).
4. Только после этого `ALT = 1.5`, `HOLD_S = 60`.

**Критерий готовности:** дрон 60 с держится в пределах ~10 см от метки, `h≈` в
логе не уползает вверх, посадка происходит сама и подтверждается ростом метки.

## Формат лога

Одна строка на цикл:

```
t= 12.3 метка  50  промах 0.07 м  h≈1.46 м  курс  +2°  → вперёд +0.05 влево -0.03 вверх +0.04
t= 12.6 метка  --  слепой кадр 1/20 (в кадре: нет)
```

Это ещё не «формат логов решений» из регламента (там про решения агента), но
привычка печатать полное состояние каждым циклом пригодится и там.

## Словарь ArUco

`DICT_4X4_1000`, **не** `DICT_4X4_50` как в «Змейке»: маркеры нашего поля —
50, 60, 62, 7 (`docs/field-map/map.txt`), а 60 и 62 в словарь на 50 элементов не
влезают. Тот же словарь стоит по умолчанию у бортовой `aruco_detect_node`
(`dictionary_id=3`), так что опознание совпадёт с бортовым.

Фильтра по ID нет вовсе — держимся над любой попавшейся меткой. Для теста это
удобнее: не надо знать, куда поставили дрон.

## Известные риски

1. **`MARKER_M` — гипотеза**, см. п. 2 порядка прогона.
2. **Метка почти наверняка будет уходить из кадра**: 4 маркера на 4,8 м поля с
   шагом 2,4 м, с рабочей высоты камера видит один или ни одного
   (`docs/field-map/README.md`). Отсюда `climb()` и `BLIND_MAX`.
3. **Повторный `navigate` в цикле.** OpenClaw предупреждает, что переиздание
   `navigate` сбрасывает траекторию C++ SpeedController и дрон бесконечно
   перезапускает заход (`docs/openclaw/snapshot/bridge/sverk_flight.py:260-264`).
   У нас команды относительные (`frame_id="body"`) и разделены `sleep`-ом на время
   прыжка — тот же режим, в котором летала «Змейка». Но если увидим «дрон дёргается
   и не доезжает» — первый подозреваемый именно это.
4. **Failsafe и KILL SWITCH** регламент требует отдельно; здесь их нет — есть
   только счётчик отказов `navigate` (5 подряд → прекращение полёта) и посадка в
   `finally`. Для тестового полёта пульт остаётся основной страховкой. На борту
   для этого есть готовые сервисы `/fmu_control/kill_switch`, `/emergency_stop`,
   `/fmu_control/force_disarm`, `/return_to_launch` — под требование регламента
   их и надо будет обвязывать, изобретать своё не нужно.

## Что подтвердилось на живом борте

Сверено 2026-07-27 на дроне `192.168.1.105` (без взлёта: selfcheck, один кадр,
детектор на синтетике). Заменяет часть гипотез, унаследованных из «Змейки»:

| Гипотеза | Как на самом деле |
|---|---|
| Камера отдаёт `yuv422_yuy2`, нужен патч | **`bgr8` 1280×960, 30 FPS.** Патч не нужен, но оставлен: он безвреден (пропускает кадр в штатный `to_cv2`) и страхует другую сборку |
| OpenCV свежий, есть `ArucoDetector` | **4.5.4** — работает запасная ветка `cv2.aruco.detectMarkers(...)`. Шим из «Змейки» оказался не перестраховкой |
| Топики ArUco как в документации (`/markers`, `/aruco_map/pose_cov`) | **Как в OpenClaw:** `/aruco/det/markers`, `/aruco/loc/pose_cov`, `/aruco/world_pose`. Расхождение из корневого `CLAUDE.md` разрешилось в пользу OpenClaw |
| Наша карта поля на борт не залита | **Залита:** `map_markers: received (4 markers)` |
| `auto_release` у `offboard_control` надо выставлять в `false` | Параметра на этой сборке **нет вовсе** (`Parameter not set`). Удержание позиции — целиком наша задача, что мы и делаем |
| `selfcheck` запускается одной командой | CLI требует поднятой ноды `self_check_node`, её нет в автозапуске; исполняемый файл называется `selfcheck`, не `selfcheck.py` |

Что осталось непроверенным, потому что дрон стоял не на поле: `MARKER_M`,
знак оси Y, реальная детекция метки в кадре. Локализация (`/aruco/loc/pose_cov`)
и VIO (`/fmu/in/vehicle_visual_odometry`) в selfcheck молчали — ожидаемо, меток в
кадре не было; проверять над полем.
