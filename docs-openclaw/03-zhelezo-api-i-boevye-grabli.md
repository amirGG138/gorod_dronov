## 1. LLM и VLM — закрывает наш пробел №2

### Шлюз «Сверх»

```
MODEL_PROVIDER=sverk
SVERK_API_BASE=https://ai.sverk.tech/v1     # OpenAI-совместимый
SVERK_API_KEY=…
MODEL=qwen35                                 # или gemma4-vlm
```

| Модель | Что | Замечания |
|---|---|---|
| `qwen35` | текстовая, семейство Qwen3 | reasoning-модель, см. грабли ниже |
| `gemma4-vlm` | gemma3-27B, и LLM, и VLM | ей проверяют кадры на пожар/груз |

Под капотом — **vLLM 0.21.0 за litellm**. Проверено авторами 2026-07-02:
`response_format = {"type":"json_schema", …}` **реально принуждается
грамматикой** (проба с `const` держится, кривая схема отдаёт 400), а старый
`json_object` — схемо-безразличный и мягкий. Вывод: для структурированного
вывода использовать `json_schema`, а не «попросить модель ответить JSON-ом».

Поддерживаются также `anthropic`, `openai`, `ollama` и детерминированный `mock`
без ключа — на моке гоняется вся сантехника, что удобно для тестов.

### Грабли промптинга

**Qwen3 съедает весь бюджет токенов на размышления вслух.** Модель нарратив на
английском пишет в `content` и до JSON не доходит: каждый вызов упирался в
`finish=length` без ответа и таймаутился. Лечение — глушить режим размышлений:

```python
{"enable_thinking": False, "chat_template_kwargs": {"enable_thinking": False}}
```

После этого — валидный JSON за 4–18 с.

**Русский язык надо требовать явно и с оговорками.** У них к системному промпту
цепляется директива: думать и писать все рассуждения и реплики по-русски, но
**не переводить** ключи JSON, значения enum, идентификаторы, координаты и код —
иначе ломается протокол. Готовый текст — `snapshot/agent/brain.py`, `_RU_DIRECTIVE`.

**С реальной моделью каждый ход упирается в `MODEL_TIMEOUT` (30 с).** Прогон
заметно длиннее мока — перед показом гонять заранее.

**Тихий отказ.** Сеть агентов `internal: true`, без выхода наружу. Без оверлея
egress вызов модели не уходит, и агенты **молча** переключаются на шаблонные
реплики — по дашборду это не отличается от настоящего прогона. Классическая
ловушка: демо «работает», а LLM в нём нет.

### Бортовой VLM на дроне

Не по сети, а на **NPU борта** — через `ros2_mcp` (в репозитории `sverk-ros2`,
`main`, коммит `8628ff4`), порт **9092**:

```python
POST http://localhost:9092/call
{"name": "vlm_query",
 "arguments": {"image_path": …, "query": …, "use_npu": true}}
→ {"content": [{"text": "{\"response\": …, \"inference_time_ms\": …}"}]}
```

Ответ модели — текст, из него регуляркой вынимается JSON. Промпт у них такой:
«На снимке сверху клетка поля. Есть ли на ней груз? Ответь ТОЛЬКО JSON:
`{"cargo": bool, "confidence": 0..1, "label": "…"}`». Таймаут 150 с — NPU не
быстрый.

## 2. Ровер: REST-API управления — закрывает наш пробел №1

`bridge/sverk_rover_bridge.py` (1084 строки) ходит в **`rover_control_api v1`
на `<ip>:8767`**. Этого API нет ни в нашей `docs-rover/`, ни в апстриме
`wodocanal/sverk_rover` (проверил дерево обеих веток — ноль совпадений).
Похоже, он ставится на площадке или появился после нашей выгрузки. **Проверить
в первый день на стенде.**

### Эндпоинты

| Метод | Что делает |
|---|---|
| `GET /v1/health` | жив ли control API |
| `GET /v1/state` | `{nav2_ready, pose:{frame_id,x,y}, map:{label}, navigation:{state}}` |
| `POST /v1/lease/acquire` | `{client_id}` → `{lease_id}` — эксклюзивная аренда управления |
| `POST /v1/lease/renew` | продлить (TTL ~5 с) |
| `POST /v1/lease/release` | отпустить |
| `POST /v1/navigation/goal` | `{request_id, x, y, yaw_deg, map_label}` — цель Nav2 в метрах карты |
| `GET /v1/navigation/status` | `{request_id, state}`; активные: `sending/accepted/navigating/canceling` |
| `POST /v1/navigation/cancel` | `{request_id}` |
| `POST /v1/teleop` | `{request_id, seq, linear_x, linear_y, angular_z, ttl_ms}` |
| `POST /v1/localization/initial-pose` | `{x, y, yaw_deg}` — переинициализация AMCL |

Лиз передаётся заголовком **`X-Control-Lease`**. Правила:

- лиз протухает примерно за 5 с → держать поток продления каждые 2 с;
- брать лиз **на одну команду** и сразу отпускать — тогда оператор или другой
  агент может вклиниться между движениями;
- `seq` в `/v1/teleop` **строго возрастающий в пределах лиза**;
- `ttl_ms` ограничен сверху **500 мс**, у них стоит 400 и пакеты шлются ~5 Гц.

Параллельно доступен веб-шлюз `rover_web` на **:8765**, `POST /api/drive/command`
→ `/cmd_vel`, deadman 0,25 с — это уже описано в нашей `docs-rover/`.

### Привязка сетки к SLAM-карте

Клетки поля пересчитываются в метры карты через калибруемый якорь:

```
map_x = map_x0 + (cx·cell)·cos θ − (cy·cell)·sin θ
map_y = map_y0 + (cx·cell)·sin θ + (cy·cell)·cos θ
```

Настраивается на лету через `GET|POST /config` моста: `cell_size`, `map_x0`,
`map_y0`, `map_yaw_deg`, `grid_nx`, `grid_ny`, `map_label`. У них на тестовом
поле было `MAP_X0=-0.46 MAP_Y0=-0.15 CELL_SIZE=0.6` и сетка 5×5 — под
регламентное поле это 0,8 м и 6×6.

### Доступ по SSH (для лечения того, что API не умеет)

```
пользователь pi / пароль raspberry, порт 22
ROS 2 Jazzy: /opt/ros/jazzy/setup.bash
рабочее пространство: /home/pi/sverk_rover/install/setup.bash
конфиг сервиса: /etc/default/rover-bringup   (там же ROVER_PROFILE, ROVER_LAUNCH_ARGS)
служба: systemctl restart rover-bringup
профили: full | mapping
сохранить карту: ros2 run rover_navigation rover_map save <name>
```

**`ROS_DOMAIN_ID=77`** прописан в `/etc/default/rover-bringup`. Голый ssh-шелл
сидит в домене 0 и **не видит ни одного топика** — любую команду `ros2` надо
оборачивать в подгрузку этого файла. На эту грабли легко потратить час.

## 3. Грабли Nav2 на ровере (всё наблюдалось живьём)

**Nav2 доезжает, но репортит `aborted`.** На нагруженном Pi цель регулярно
отваливается без причины. Лечение из их кода: допуск по факт-позе
(`GOAL_TOL = 0.22` м — если ровер уже там, считаем прибытием) плюс **один
авто-ретрай** цели.

**«A navigation goal is already active».** Осиротевшая цель (перезапуск моста
посреди поездки, чужая команда) блокирует все новые. Отменить и **дождаться**,
пока статус реально перестанет быть активным, а не просто послать cancel.

**Залипание в `canceling`.** `cancel_goal_async` по мёртвому handle не
резолвится — API виснет навсегда. Лечится передёргиванием lifecycle
`/bt_navigator` (deactivate → activate), а в тяжёлом случае только перезапуском
`rover-bringup`.

**Nav2 недоактивируется после перезапуска bringup.** Bond timeout у
lifecycle-менеджера: `bt_navigator`/`planner_server` висят в `inactive`, при
этом control API отвечает `nav2_ready = true`, а цели молча отклоняются
(«Action server is inactive»). Нужно дожимать активацию **по каждой ноде** с
ретраями: `map_server amcl planner_server controller_server smoother_server
behavior_server bt_navigator waypoint_follower`.

**Курица и яйцо после перезапуска.** Без позы AMCL нет TF `map→odom`, а без него
не активируется planner. Значит: сначала восстановить последнюю известную
initial pose, потом активировать Nav2.

**После смены профиля bringup поднимается ~40 с, AMCL пуст.** Не отказывать
мгновенно — ждать готовности (`nav2_ready` И `pose.frame_id == "map"`), у них
таймаут ожидания 25 с.

**Одно движение за раз.** Вторая команда во время поездки должна получать
честный 409 («едет к цели, N с — жми stop»), иначе приходит мутный отказ лиза.

## 4. Грабли дронов PX4 (`sverk_interfaces`)

**Мультиинстанс PX4 SITL не работает.** Инстансы `i ≥ 1` не проходят
OFFBOARD-хендшейк (`Failed to switch to OFFBOARD mode: Timeout` → AUTO.LOITER →
disarm). Авторы проверили, что это **не лечится** изоляцией: свои gz-партиции,
свои DDS-домены, свои `MicroXRCEAgent` на портах 8888+i, меньше дронов, низкая
нагрузка — всё равно летит только инстанс 0. Поэтому авторы «Сверх» и ушли на
MAVLink для мультидрона в симуляции.

**На реальном железе этой проблемы нет** — каждый борт со своим PX4, своим
`offboard_control` и своим uXRCE-агентом является «инстансом 0» на своей
машине. То есть путь `sverk_interfaces`, доведённый на одном дроне, — это ровно
то, что крутится на каждом борту.

**`auto_release:=false` при запуске `offboard_control`.** Иначе нода отпускает
цель по прибытии, поток сетпоинтов прекращается и дрон проседает. С `false`
последний `navigate` транслируется бесконечно — это и есть удержание позиции
между перелётами.

**Нельзя переиздавать `navigate` в опросе `reached()`.** Каждый повторный вызов
переинициализирует траекторию в C++-контроллере скорости, и дрон бесконечно
начинает заход заново, никуда не двигаясь. `goto()` издаёт `navigate` **ровно
один раз**, `reached()` — чистая проверка без побочных эффектов.

**Дрон выпадает из OFFBOARD в простое.** Между командами разведки борт может
уйти в AUTO.LOITER и дизармиться (наблюдалось на 3 из 4 дронов под нагрузкой
общего DDS). Keep-alive: опрашивать `armed`/`mode` и переиздавать
`navigate(auto_arm=True)` **только когда действительно выпал**. Если бить
вслепую по таймеру — попадёшь в предыдущую грабли.

**`auto_arm=True` всегда.** Самолечение: если дрон просел на землю и
дизармился, обычный `navigate` вернёт «Copter is not in OFFBOARD mode, use
auto_arm?» и борт не восстановится уже никогда.

### Кадры координат — самое хрупкое место

| Кадр | Что это | Когда доступен |
|---|---|---|
| `map` | ENU от точки спавна, из EKF | **всегда** |
| `aruco_map` | по маркерам на полу | только когда маркеры в кадре |
| `body` | относительный | всегда |

Лётный рецепт для реального борта: **взлетать в `body`** (маркеры с земли
обычно не видны), на высоте **перехватываться в `aruco_map`** — прочитать
позицию по маркерам и выдать удержание там. Если через `FRAME_WAIT_SEC` (8 с)
телеметрии рабочего кадра нет — честно шуметь в лог и не лететь вслепую.

Пересчёт для `sverk_interfaces` (у них внутри ENU, снаружи локальный NED):

```
pos_ned = (map.y, map.x, −map.z)
goto(north, east, up) → navigate(x=east, y=north, z=up, frame_id="map")
```

**Проверять на стенде в первую очередь** (список из `BRIDGE-NODE-STATUS.md`):
имена кадров (`map` / `aruco_map` / `aruco_map_0`), **знаки осей** (знак Y на
разных полигонах разный — проверять по одной клетке на малой высоте), момент
перехвата из body в aruco, таймауты (`BRIDGE_TIMEOUT` 120 с — реальный перелёт
медленнее мока, при меньшем агент отваливается посреди полёта).

`SPAWN_X`/`SPAWN_Y` обязаны совпадать с точкой спавна: дефолт `0` уводит борт за
поле и даёт серые пустые снимки. На это уже наступали.

### Реальность вместо доверия

Отдельный «gate реальности»: `bridge/aruco_cell.py` смотрит, какой маркер под
камерой, и `GET /pose` возвращает `aruco_cell`, `on_field`, `reality_ok`. Дрон
поднимает находку **только** если камера подтверждает, что он действительно над
заявленной клеткой. Иначе находка отзывается (`reality_reject`) и дрон
переснимает. Ловит дрейф EKF, вынос за поле и ошибки после kill switch.

## 5. Раскладка на борту

```
Orange Pi 5 = full_system_real.launch.py (ROS 2: камера + aruco-локализация
                                          + offboard_control + sverk_interfaces)
            + bridge_node.py (FLEET=city)          [docker или нативно]
            + мозг (python-петля / PicoClaw)       [docker]
Диспетчер   = ПК или отдельный Pi: LLM-петля + blackboard/hub + дашборд
Ровер       = свой борт: Nav2 + лидар, тот же HTTP-контракт
```

Образы уже мультиарх: `agent/Dockerfile` и `bridge/Dockerfile` — на
`python:3.12-slim`, **только stdlib**, поэтому собираются под arm64 без индекса
пакетов. `drone/Dockerfile` собирается через `buildx --platform linux/arm64`.

VLM крутится на NPU борта, а не по сети. Мозги общаются через hub/blackboard.

### Управление во время попытки

- **Пауза/возобновление всей миссии** — `POST /pause`, дроны садятся, фазовая
  машина замирает, дедлайны сдвигаются на длительность паузы. Переживает
  kill switch (дрон приземлился где угодно).
- **Замена АКБ на дроне** — `POST /pause` (посадка + заморозка), затем
  `/takeoff`.
- **Произвольный старт / восстановление после kill switch** — поставить дрон на
  любую клетку и `POST /set_cell {"cell":[x,y]}`; мост перекалибруется, сценарий
  продолжается оттуда. Aruco-проверка подтверждает, что он действительно там.
- **Посадка домой** — `POST /land {"home": true}`.

Это прямо отвечает регламентному требованию «заряд ≥ 40 % перед попыткой»:
замена батарей не ломает прогон.
