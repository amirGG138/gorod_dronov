

# DIMENSION: blackboard
SUMMARY: The FileBoard core is solid where it matters most for the local studio demo: state writes are atomic (tmp + os.replace), message filenames cannot clobber across agents, and events.jsonl appends use a single O_APPEND write(). The weak spots are everything around that core: HttpBoard has lost parity with the code that now calls the board (bb.root / read_json), so any remote drone crashes at boot — distributed mode is dead on arrival; run_log's buffered multi-process appends can interleave llm.jsonl; the SSE tailer does not survive the reset_runtime truncation it is documented to survive; and context_budget.clip_transcript truncates the wrong end of the transcript. Handoff claims 6, 7, and 8 in this area are all CONFIRMED still true, with concrete impact paths traced (debate floor matching by message id, ts-sorted debate transcripts).

## [major] [CONFIRMED] HttpBoard drones crash at startup: run_log.refresh_from_bb calls bb.root/bb.read_json which HttpBoard does not have
file: agent/run_log.py:65
desc: loop.py:235 calls run_log.refresh_from_bb(bb) unconditionally at the top of every cycle, OUTSIDE the resilience try/except (which starts at loop.py:254). refresh_from_bb does `bb.read_json(bb.root / "state" / "current_run.json", {})`. HttpBoard (agent/bb.py:212-298) has neither a `root` attribute nor a `read_json` method, and RUN_LOG defaults to enabled (run_log.py:18). So any drone started with HUB_URL set (docker-compose.drone.yml, `make drone`) raises AttributeError on its first loop iteration and the process exits; with `restart: unless-stopped` (docker-compose.drone.yml:29) it crash-loops forever. Even if RUN_LOG=0 were set, painting/studio roles would still fail every cycle inside roles.step because they call `ctx.bb.read_json(ctx.bb.root / "config.yaml.json")` (agent/roles/painter_agent.py:40, studio_chat.py:28, painter_palette.py:14, collab_paint.py:45, collaborative.py:15) — the loop's try/except catches that, so the drone would idle forever emitting error events. Distributed (HttpBoard) mode is 100% broken for all tasks; only the local FileBoard demo works.
fix: Give run_log.refresh_from_bb a hasattr guard (or add read_json/root no-ops to HttpBoard), and route role config reads through a board method that HttpBoard implements (e.g. GET /state/config). Add a smoke test that boots one HttpBoard drone against the hub.

## [major] [PARTIAL] clip_transcript truncates the NEWEST end of the transcript when over the char budget
file: agent/context_budget.py:34
desc: clip_transcript keeps the last TRANSCRIPT_MAX_LINES lines (newest 500) but then passes the joined text through clip_text, which keeps the FIRST max_chars characters (`t[:max_chars-1] + "…"`, line 27). Lines are built oldest→newest (agent/roles/painter_palette.py:107-122 session_transcript iterates ctx.messages in board order), so when a session transcript exceeds TRANSCRIPT_MAX_CHARS=28000 the MOST RECENT messages are the ones cut off. Painters then negotiate against a stale view of the conversation and never see the latest turns — in a long studio/painting session this silently degrades convergence (drones can miss recent agreements/'done' signals). Latent in short demo runs (triggers only >28KB), guaranteed wrong once it triggers.
CORRECTION: The truncation-direction bug (keeping oldest instead of newest) is real in clip_transcript/clip_text, but it is unreachable dead code: its only caller, session_transcript, is never invoked anywhere in the codebase. The real negotiation/painting/debate paths all use negotiation_messages(), which does not use clip_transcript and applies no newest-end truncation. Severity should be downgraded from 'major' to trivial/informational (latent defect in unused helper), and the impact claim ('painters negotiate against a stale view', 'never see latest turns', 'degrades convergence') should be removed since it cannot occur at runtime.
fix: In clip_transcript, trim from the head: `return body if len(body) <= TRANSCRIPT_MAX_CHARS else "…" + body[-(TRANSCRIPT_MAX_CHARS-1):]` (keep the newest tail).

## [major] [UNVERIFIED] run_log._append_jsonl: concurrent multi-process appends can interleave and corrupt llm.jsonl
file: agent/run_log.py:35
desc: Every agent process appends to the SAME run files (all attach to the run dir via current_run.json). _append_jsonl uses a buffered text handle (`open(path, "a")` + fh.write). With RUN_LOG_FULL defaulting to on (run_log.py:102), llm.jsonl records embed the full system prompt (soul up to 12000 chars), full message history (transcript up to 28000 chars) and full response — lines of 30-80KB. TextIOWrapper/BufferedWriter flushes such a line in multiple write() syscalls (~4-8KB chunks), so two agents logging simultaneously (common: parallel painter turns hitting sverk) can interleave chunks mid-line, producing corrupt JSONL. llm.jsonl is the primary replay/debug artifact per the handoff ('replay llm.jsonl to debug'), so corruption defeats the debug pipeline exactly when it is busiest. bb.append_event got this right (single os.write, bb.py:204-209); run_log did not.
fix: Mirror bb.append_event: encode the line, then os.open(path, O_WRONLY|O_CREAT|O_APPEND) + a single os.write. (A single write() to a regular file is serialized by the kernel regardless of size.) Or give each agent its own llm-<agent>.jsonl.

## [major] [UNVERIFIED] SSE tailer never rewinds after reset_runtime truncates events.jsonl — dashboards miss the start of every rerun
file: viz/server.py:335
desc: reset_runtime truncates events.jsonl in place, with an explicit comment 'keep the file so tailers/SSE stay attached' (bb.py:82-87). But the SSE loop keeps a byte cursor `pos` that only grows: after truncation, `fh.seek(pos)` seeks past the (now smaller) EOF and reads nothing, so a connected dashboard receives ZERO events from the new run until the file grows back past the old offset — and the first thing it then receives is a partial line starting at an arbitrary byte offset (garbage JSON). This fires in the flagship flow: open dashboard, hit /rerun (viz/server.py:189-201 calls BB.reset_runtime()), coordinator starts a new run — the browser silently shows nothing (the canvas_clear + phase INIT events appended right after the reset land at offsets < pos and are skipped). Only a manual page reload (fresh SSE with pos=0) recovers.
fix: Before seeking, check `size = os.stat(EVENTS).st_size; if size < pos: pos = 0` (file was truncated → replay from start). Optionally emit a 'reset' SSE event so the frontend clears state.

## [major] [UNVERIFIED] [handoff #7 CONFIRMED] Second-granularity timestamps + per-process seq: message ordering is non-causal within a second; debate sorts by ts
file: agent/bb.py:27
desc: STATUS: still true, and slightly worse than the handoff states. now_iso() has whole-second resolution (bb.py:26-27). Message filenames are `{safe_ts}-{seq:04d}-{from}-{type}.json` (bb.py:173-174) and list_messages sorts by filename (bb.py:180) — but `_seq` is PER PROCESS (each local agent is its own python process per scripts/run_local.sh:40-83), so within the same second, ordering is decided by each writer's private counter, not by write time: painter-2's later message with seq 0003 sorts before painter-1's earlier one with seq 0007. Consumers that sort by ts inherit the same tie problem: moderator.py:99 and 124-125 sort arguments+openings by m['ts'] to build the LLM transcript, and debate_common.py:150 picks 'most recent' floor by (round, ts). Studio chat's position-based logic (studio_chat.py:94-104) sidesteps ts ties as the handoff claims, but its positions come from the same filename-sorted list, so cross-agent same-second inversions still leak into `others_after` reply detection. In distributed mode it degrades further: ts is stamped by the drone's own clock (loop.py:289) so cross-host skew scrambles ordering beyond one second.
fix: Use sub-second timestamps (datetime.now(timezone.utc).isoformat(timespec='microseconds')) in now_iso, or have the single hub/board assign a monotonic global sequence at write time and sort consumers by it.

## [major] [UNVERIFIED] [handoff #8 CONFIRMED] _seq resets on restart → message-id collisions; traced impact: debate floor/answer matching keys on id
file: agent/bb.py:39
desc: STATUS: still true. Blackboard._seq starts at 0 per process (bb.py:39) and ids are `msg-{from}-{seq:04d}` (bb.py:172). With RESET_ON_START=0 (documented knob, loop.py:189), a coordinator restart mid-run reissues ids already on the board. Concrete breakage traced: the debate engine matches ARGUMENTs to FLOOR grants by id — debate_common.py:156-161 (`reply_to == fid`) and moderator.py:254-256 (`f.get("id") not in answered`). A reissued FLOOR id that collides with an old, already-answered floor makes the NEW floor look instantly answered, so the moderator skips that debater's turn. Same failure in distributed mode WITHOUT any opt-out: the hub process owns _seq for all POSTed messages (viz/server.py:52 `BB = Blackboard()`), so a hub restart mid-run resets the counter while messages/ persists on the volume. Also noted: the hub is a ThreadingHTTPServer (viz/server.py:348), so `self._seq += 1` (bb.py:169) is an unsynchronized read-modify-write across handler threads — currently benign only because id/filename both include `from` and each drone posts sequentially. HttpBoard._seq (bb.py:225) is dead code, never used.
fix: Seed _seq from the board at startup (max existing seq parsed from messages/ filenames) or use uuid4 suffixes for ids; guard the hub's counter with a lock.

## [major] [UNVERIFIED] Quadratic board re-reads: every agent re-opens and re-parses every message file every poll cycle; the incremental API is dead code
file: agent/loop.py:97
desc: build_ctx calls bb.list_messages(), bb.read_all_progress(), bb.read_assignments(), bb.read_world() every cycle (loop.py:96-100), and list_messages opens + json-parses EVERY file in messages/ (bb.py:178-184). With N messages and A agents polling at 1s, that is N*A file opens+parses per second, and N grows through the run → O(N²) total parse work per agent over a run. KEEP_ALIVE agents keep doing this forever after DONE (loop.py:241-244 re-reads the whole board before checking DONE). At studio scale (hundreds of messages, 5-10 agents) this is hundreds to thousands of opens/sec late in a run — works on a warm page cache but is significant, growing debt, and it multiplies in-run latency for roles that also re-derive transcripts from ctx.messages each cycle. Ironically bb.py already has an incremental API for exactly this — messages_since (bb.py:186-197) and wait_for_change/_signature (bb.py:335-355) — and repo-wide grep shows ZERO callers: it is dead code (and messages_since has its own mtime-tie loss window if ever used as-is).
fix: Cache parsed messages keyed by filename (filenames are immutable append-only), only reading new files each cycle; or wire up messages_since with a (name-set, mtime) cursor. Delete wait_for_change/_signature or use them.

## [major] [UNVERIFIED] HttpBoard writes are silently dropped on hub error — no retry, caller told it succeeded
file: agent/bb.py:288
desc: HttpBoard.write_message swallows any exception and returns the original msg as if stored (bb.py:288-292); write_progress and append_event likewise pass silently (bb.py:282-286, 294-298). No retry, no error event, no local spool. For messages, role idempotence mostly self-heals — roles re-check the board via has_posted (roles/__init__.py:20-29) and re-post next cycle if their message is absent — but that recovery is accidental, unlogged, and races phase deadlines: a VOTE dropped during a hub blip near the vote deadline is simply never counted, and the coordinator's deadline fallback silently decides with fewer ballots. write_progress is worse: roles write progress on state transitions and do not re-verify it against read_all_progress, so a dropped progress POST can stall a phase until its deadline fires. The docstring frames this as 'a flaky link never crashes a drone', but there is no observability at all (not even a local print), so distributed-mode result skew is undetectable. Nit in the same area: _get (bb.py:237-242) returns None instead of the default if the hub ever responds with JSON null and the default is a dict.
fix: Retry once or twice with short backoff; on final failure print and enqueue a local retry buffer flushed next cycle, and emit a local error event so drops are visible.

## [minor] [UNVERIFIED_LOW_PRIORITY] events.jsonl '< PIPE_BUF' atomicity invariant is false in practice (and ensure_ascii inflates Russian events ~6x)
file: agent/bb.py:204
desc: The module header (bb.py:13-14) and append_event comment claim event lines stay under PIPE_BUF=4096 so the O_APPEND write is atomic. Real lines routinely exceed that: thought_end events carry text≤800 + thinking≤2400 chars (loop.py:170-174), and json.dumps defaults to ensure_ascii=True, so Cyrillic (the studio's language) becomes \uXXXX — 6 bytes per char → ~14KB lines; message events embed full shape payloads (polys) which are also multi-KB. Nothing actually breaks — a single os.write() to a regular file is serialized by the kernel regardless of size (PIPE_BUF only bounds pipes) — but the documented invariant is wrong (loop.py:106 repeats it), and the ASCII-escaping bloats events.jsonl and SSE traffic ~6x for Russian text. The same false comfort led run_log to assume appends were safe (see the llm.jsonl interleaving finding, where buffered I/O makes it genuinely unsafe).
fix: Fix the comments to cite single-write() atomicity on regular files, and pass ensure_ascii=False in append_event (SSE and the frontend are UTF-8 throughout).

## [major] [CONFIRMED] Floor-expiry hole: two debaters can hold the floor simultaneously
file: agent/roles/debate_common.py:139
desc: In sequential (moderated/round_robin) debate, the moderator enforces one live speaker by skipping expired floors and granting the next one (moderator.py:256 `live = [f for f in floors_round if f.get('id') not in answered and not _floor_expired(f)]`). Not the flagship (studio uses stigmergic chat, no floors), so major not critical.
CORRECTION: The finding is accurate; only a minor caveat. Severity "major" is defensible but debatable: the consequence is a soft/temporal invariant breach (one extra late argument on the non-flagship debate path) — no crash, deadlock, or data corruption — and it only triggers when a debater's LLM turn exceeds the 60s floor deadline AND another debater is still un-granted in the round. A reviewer could reasonably rate it minor. This is not enough to downgrade the finding; the described mechanism, code citations, and root cause are all correct.
fix: In my_open_floor, drop floors whose payload deadline has passed (reuse a _floor_expired check), so an expired grant is no longer 'my open floor'.

## [major] [PARTIAL] Event lines exceed the PIPE_BUF atomicity bound the SSE feed depends on
file: agent/bb.py:203
desc: append_event uses json.dumps with default ensure_ascii=True, so Cyrillic characters expand ~6x into \uXXXX escapes. thought_end events carry thinking up to 2400 chars plus text up to 800 chars (loop.py:139-143, 170-174), producing event lines on the order of 15 KB -- far beyond the PIPE_BUF=4096 the code explicitly assumes (bb.py:203-208 comment). PIPE_BUF atomicity applies to pipes/FIFOs, not regular files. events.jsonl is a regular file, and on Linux (the documented/deployed platform) each O_APPEND write() holds the inode lock for its full duration, so concurrent multi-process appends of any size are serialized and land contiguously at EOF. The SSE tailer therefore always reads complete newline-terminated lines and never a truncated JSON fragment. The correct, lower-severity fix is cosmetic/robustness: pass ensure_ascii=False to shrink lines and correct the misleading comment; optionally loop on os.write's return value for defensiveness. This is not a major SSE-correctness defect on Linux regular files. (Genuine atomicity loss would only arise on NFS-backed storage, which the finding does not claim and which is not the setup here.)
fix: Cap serialized event line length below PIPE_BUF (or write with a lock/rename-append for large lines), and/or store large thinking payloads out-of-band and reference them from the small feed event.
