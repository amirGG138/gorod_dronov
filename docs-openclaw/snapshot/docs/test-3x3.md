# test-3x3 — скан 3×3 одним дроном + спор двух пилотов

Маленький **end-to-end смоук-тест всего стека** на реальном мате 3×3: агенты,
живой спор LLM, покадровое фото, пауза/шаг/сброс и **реальный борт**. Без ровера
и без mission-детекции (пожар/доставка убраны) — задача одна: облететь и снять все
9 клеток, а два агента-пилота спорят, каким маршрутом это делать.

## Карта (реальный мат, `expo_map.txt`)

5 ArUco-маркеров, размер 0.25 м, сетка `CELL=0.6 м`, `origin=-0.6 м`, высота ~1 м,
map-фрейм. Клетка = `round((world - origin)/CELL)`:

```
id 4  ( 0.000,  0.000) -> [1,1]  центр (старт)
id 27 ( 0.601,  0.601) -> [2,2]
id 15 (-0.601, -0.605) -> [0,0]
id 2  (-0.601,  0.601) -> [0,2]
id 42 ( 0.601, -0.605) -> [2,0]
```

Маркеры только в углах и центре; на рёбрах `[1,0][0,1][2,1][1,2]` маркера нет —
там позиция падает на EKF. Файлы: `test_fixtures/test-3x3/map.json` и
`test_fixtures/test-3x3/markers.txt`. Если реальные замеры отличаются — правятся
только `CELL_SIZE / FIELD_ORIGIN / TAKEOFF_Z` и `markers.txt`, код не трогается.

## Архитектура

Задача `scan_debate` (модуль `agent/roles/scan_debate.py`). Три роли:

| роль | агент | что делает |
|------|-------|-----------|
| `coordinator` | coordinator | владеет фазами INIT→DEBATE→SCAN→DONE, сводит маршруты, сеет `state/control.json` (кто «у руля») |
| `controller` ×2 | pilot-a / pilot-b | предлагают РАЗНЫЕ маршруты (A=периметр, B=спираль из центра) и спорят живым LLM |
| `flyer` | drone-1 | **единственный борт**: читает `control.json`, летит маршрут активного пилота, снимает клетки |

Только у `flyer` есть bridge → **нет драки двух хозяев за PX4**. Кто «у руля»
задаёт `state/control.json`; оператор переключает его в паузе — и борт летит
маршрутом другого пилота.

## Три уровня работы

- **mock, без борта** (по умолчанию): детерминированные разные маршруты +
  шаблонный спор, полёт СИМУЛИРУЕТСЯ — фронт/переключение/анимация видны.
- **живой LLM, без борта**: `MODEL_PROVIDER=sverk` + `SVERK_API_KEY` — пилоты
  спорят по-настоящему; полёт всё ещё симулируется.
- **+ реальный борт** на `fleet:9001`: реальный полёт + фото по map-фрейму, 1 м.

## Запуск (симуляция стека, без железа)

```bash
bash scripts/test_3x3.sh                      # mock-мозг, offline
MODEL_PROVIDER=sverk bash scripts/test_3x3.sh # живой спор LLM
# или: make local-test3x3
```

Фронт — **Test Front**: `http://localhost:8095/test` (или `/` — авто-роут по
сценарию). Всё в один экран, ползунок масштаба поля. Демо:

1. В чате пилоты спорят, предлагают порядок облёта.
2. Дрон 🚁 летит маршрут активного пилота, клетки помечаются 📷 (клик = кадр).
3. **Пауза** (⏸) → в карточке «Управление дроном» **отдать руль** другому пилоту
   → **▶/⏭** → дрон летит уже по ЕГО маршруту. **Reset** (⟲) — прогон заново.

## Подключить РЕАЛЬНЫЙ дрон — загрузка ноды по SSH

Дрон уже с нашим образом (sverk ROS2). Догружаем **только нашу ноду** — bridge
(`real_bridge.py` + зависимости) и карту 3×3 — стартуем против реального лётного
стека (`FLIGHT_BACKEND=sverk` → `sverk_interfaces` → PX4 FMU, map-фрейм, ~1 м) и
говорим борту его клетку. Одной командой с машины оператора:

```bash
DRONE=sverk@<ip-дрона> bash scripts/deploy_drone.sh
# опции: SVERK_CT=sverk_sitl INSTANCE=0 START_CELL=1,1 FLIGHT_BACKEND=sverk TAKEOFF_Z=1.0
# если sverk крутится не в докере, а прямо на хосте дрона:  DRONE=... SVERK_CT="" bash scripts/deploy_drone.sh
```

Что делает `deploy_drone.sh`: `scp` файлов ноды на дрон → `docker cp` в
sverk-контейнер → `scripts/_drone_bridge_launch.sh` внутри контейнера (env под
3×3: `CELL_SIZE=0.6 FIELD_ORIGIN=-0.6 TAKEOFF_Z=1.0 CAM_OFF*=0
ARUCO_MARKERS=…/markers.txt`) → `healthz` → `set_cell [1,1]` (центральный маркер
id4). Файлы ноды («что догружаем»): `bridge/{real_bridge,sverk_flight,
fleet_flight,mock,aruco_cell}.py` + `test_fixtures/test-3x3/markers.txt`.

### То же вручную (по шагам, внутри sverk-окружения на дроне)

```bash
# 1) мост к борту (map-фрейм, 1 м):
FLIGHT_BACKEND=sverk PORT=9001 INSTANCE=0 OFFBOARD_NS=/px4_0 \
  CELL_SIZE=0.6 FIELD_ORIGIN=-0.6 TAKEOFF_Z=1.0 TAKEOFF_Z_M=1.0 CAM_OFFX=0 CAM_OFFY=0 \
  ARUCO_MARKERS=/tmp/markers.txt python3 /tmp/real_bridge.py &
# 2) сказать борту, над какой он клеткой (id4 = [1,1]):
curl -s localhost:9001/set_cell -d '{"cell":[1,1]}'
```
`FLIGHT_BACKEND=sverk` — реальный offboard через `sverk_interfaces`; `mavlink` —
прямой MAVLink-фолбэк (SITL). Нейдир-камера: `CAM_OFF*=0`.

### Агенты (спор + фронт) — на машине оператора

- Навести flyer на дрон: в `docker-compose.test.yml`, сервис `flyer` →
  `BRIDGE_URL: http://<ip-дрона>:9001` (или подключить sverk-контейнер дрона к
  сети `mesh` под алиасом `fleet` и `BRIDGE_URL=http://fleet:9001` — как в
  локальном стеке).
- `MODEL_PROVIDER=sverk bash scripts/test_3x3.sh`. Фронт: `:8095/test`.

### Сеть и камера (важно)

- **Сеть.** Мост слушает `0.0.0.0:9001` внутри sverk-контейнера. flyer-агент
  должен дотянуться: либо порт `9001` опубликован на хост дрона (LAN), либо
  sverk-контейнер в общей docker-сети с агентами (алиас `fleet`).
- **Камера.** `real_bridge.py` берёт кадр из **gz-топика** (SITL). Полёт, облёт
  клеток и `set_cell` работают на реальном FMU через sverk offboard независимо от
  камеры; но `/photograph` вернёт `captured:false` и cv2-реалі-чек не сработает,
  пока источник кадра не наведён на РЕАЛЬНУЮ камеру дрона (ROS2 image-топик) —
  это единственная точка интеграции под живую камеру. Если дрон крутит полный
  образ с SITL+gz, gz-камера работает как есть. *(Адаптер под реальную камеру —
  отдельная небольшая доработка `real_bridge.py`, готов сделать по запросу.)*

Реалі-чек: `flyer` через cv2-ArUco сверяет, что камера подтверждает клетку
(индикатор «реалі-чек» в карточке борта на фронте). Пауза сажает борт, снятие
паузы — взлёт и ресинк позы из телеметрии.
