### 1.1 city_missions — полный сценарий в mock (одна команда)
```bash
python3 scripts/city_e2e_mock.py          # печатает таймлайн доказательств + PASS
python3 -m unittest discover -s tests      # 62/62 тестов зелёные
```
Автономный прогон по регламенту, без роботов и без LLM:
- планировщик выбирает порядок миссий (пожар → доставка), объясняет причины;
- ровер **предзаряжается на весь план** (правило резерва на возврат к зарядке);
- **пожар уровня N = N циклов** `башня → 3с LED-стоп → пожар` (2 цикла для city-1);
- **вспомогательный дрон** находит человека в окне (FIRE_SEARCH);
- **доставка**: 5с погрузка+LED → эскорт **сзади, отставание ≤2 клетки** → финиш;
- **маршрут доставки не идёт через непотушенный пожар** (проверено на коридоре);
- энергия **никогда не уходит в минус**, укладываемся в **15 минут** (235с для city-1).

Ядро (`agent/roles/city_world.py`, `city_executor.py`) — чистая логика без
зависимостей от полёта: `WorldModel`, дорожный A* (объезд зданий), `EnergyLedger`,
компиляторы `fire_route`/`delivery_route`, `rank_missions`, валидаторы 3с/5с. Это
**переиспользуется на железе** (роль `city_rover` дергает те же шаги через bridge).
Покрыто 20 тестами включая обязательные негативы аудита (2.9с/4.9с не засчитаны,
маршрут через пожар отклонён, движение при 0 энергии заблокировано).

### 1.2 Реальный полёт одного дрона через `sverk_interfaces` (SITL)
Доказано ранее (`bridge/sverk_flight.py`, `FLIGHT_BACKEND=sverk`): взлёт на 1.5м,
перелёт по клеткам (все REACHED), посадка — всё через `/px4_i/navigate` →
`offboard_control` → uXRCE-DDS → PX4. Камера + cv2-aruco reality-gate живые.

### 1.3 Карта Domiki (полное поле)
`Domiki.glb` (glTF, 32МБ) проверен: **9 мешей, 11 встроенных текстур**, 7 домов +
земля + стены. **4 крыши несут реальные ArUco-маркеры** (материалы Top Blue/Pink/
Cyan → «крыша дом1/2/3 с арукой»), **3 крыши без аруки** (NoMap). 4 aruco-площадки
= 4 площадки дронов по регламенту. Земля `pole-gorod` = полная карта 6×6 (жёлтый/
красный/синий/зелёный районы, центральная зарядка-батарея, водонапорная башня).
Габарит **4.79×4.79 м = ровно 6×6 при 0.8 м/клетка** (масштаб регламента, scale 1).
gz Harmonic 8.14 грузит `.glb` напрямую — модель-обёртка `bridge/gazebo/models/
domiki_city` спавнится без ошибок ассимпа.

## 2. Что заблокировано и ПОЧЕМУ это не проблема железа

### 2.1 4 дрона одновременно в SITL — летит только инстанс 0
Инстансы PX4 SITL `i≥1` не проходят OFFBOARD-хендшейк
(`Failed to switch to OFFBOARD mode: Timeout` → AUTO.LOITER → disarm). Проверено,
что это НЕ лечится изоляцией: свои gz-партиции + свои DDS-домены + свои
MicroXRCEAgent (порт 8888+i) + меньше дронов (даже 2) + низкая нагрузка (7/20 ядер)
— всё равно только инстанс 0. Это причина, по которой авторы sverk ушли на MAVLink
для мультидрона в симуляции.

**Ключевой момент: на реальном железе этой проблемы НЕТ.** В SITL 4 инстанса делят
один хост и одну симуляцию. На стенде **каждый дрон — отдельный Orange Pi со своим
PX4, своим `offboard_control`, своим uXRCE-агентом** — каждый борт это «инстанс 0»
на своей машине. Одиночный путь `sverk_interfaces`, который доведён до рабочего
(п.1.2), — это **ровно то, что крутится на каждом борту**. Поэтому масштабирование
на реальные дроны идёт по этому пути, а не по SITL-мультиинстансу.

## 3. Совместимость с ROS2-образом

| Слой | Образ / где | Арх | Статус |
|---|---|---|---|
| SITL-сим (dev-PC) | `sverk/ros2:sitl` | **amd64**, ROS2 Humble | только для разработки на ПК |
| На дроне (борт) | `full_system_real.launch.py` | arm64 (Pi) | камера (libcamera/mipi) + `aruco.launch.py` (карта+детект+локализация → `/aruco/world_pose`) + `offboard_control` + `sverk_interfaces` |
| Наш bridge на борту | `bridge/ros2/bridge_node.py` | arm64 | код-комплит, режим city; **[СТЕНД]** не гонялся вживую |
| Мозг (LLM-петля) | `agent/` (picoclaw-agent) | any | Python-stdlib, портируется |

`bridge_node.py` — это единственный шов сим↔железо: тот же HTTP-контракт, что у
`bridge/mock.py`, реализован поверх `sverk_interfaces.init()` (navigate/land/
get_telemetry/led/take_picture + бортовой VLM через ros2_mcp). Агент/PicoClaw при
переходе на железо **не меняются**. Что нужно дописать в нём для city_missions:
эндпоинты ровера (`/navigate` многошаговый, `/stop`, подтверждённый `/dwell` с
доказательством `pose_stable_Ns` + LED, статус/heartbeat/estop) и роль эскорта.
Его докстринг уже помечает **[СТЕНД]**: имена кадров (`aruco_map`/`map`), знаки
осей, калибровку `ARUCO_OFFX/Y` по реальной камере.

## 4. Orange Pi 5 в докере — реалистично, архитектура уже заложена

**Мультиарх подтверждён в коде:**
- `drone/Dockerfile` — явно `linux/arm64,linux/amd64` (Pi 4/5), сборка через
  `docker buildx --platform linux/arm64`.
- `agent/Dockerfile`, `bridge/Dockerfile` — база `python:3.12-slim` (есть arm64),
  **только stdlib** → без индекса пакетов, собирается на arm64 «из коробки».
- `drone/entrypoint.sh` адаптируется по `AGENT_ID/ROLE/TASK/FLEET(city|painter)`.

**Схема на борту (per-Pi, без gz/mavlink/SITL):**
```
Orange Pi 5  =  full_system_real (ROS2: camera + aruco-локализация + offboard_control)
              + bridge_node.py (FLEET=city, sverk_interfaces)   [docker или нативно]
              + мозг (picoclaw / python-loop)                    [docker openclaw-drone]
Диспетчер   =  центральный ПК или один Pi: LLM-петля + blackboard/hub + dashboard
```
Каждый Pi — один дрон = «инстанс 0» → SITL-проблема мультиинстанса не возникает.
VLM крутится на **NPU** борта (ros2_mcp `vlm_query`), не по сети. Мозги общаются
через hub/blackboard (`make drone ROLE=… HUB_URL=…`).

**Бюджет ресурсов (ориентир, требует замера [СТЕНД]):** Pi5 8×arm64 + NPU. На борт:
ROS2 Humble + offboard + один камера-поток + aruco + VLM(NPU) + лёгкая python-петля.
Один дрон на борт — тесно, но реалистично; тяжёлого (gz-физики, 4× инстансов) на
борту нет. Ровер (Nav2+лидар) — отдельный борт/RDK.
