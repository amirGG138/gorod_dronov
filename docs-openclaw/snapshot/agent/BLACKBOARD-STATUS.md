## Подтверждённый дефект 1: зелёные клетки не сбрасываются между прогонами

**Симптом.** После второго и последующих `make mission-rerun` на фронте
(`/survey`, `/survey-commerce`) остаются зелёные клетки от прошлого прогона.
Дашборд показывает покрытие, которого в текущем прогоне ещё нет.

**Где.** Это дефект ФРОНТА, не доски. `viz/survey.html`, функция `applyWorld`:

```js
Object.entries(w.cells||{}).forEach(([k,v])=>{
  const c=k.split(",").map(Number);
  if(CELLS[k]!==v.status)setCell(c,v.status);
});
```

Цикл идёт только по клеткам, которые ЕСТЬ в новом `world.json`. Когда
`reset_runtime()` удаляет `state/world.json`, новый мир приходит почти пустым —
и про старые ключи никто не вспоминает. Локальный `CELLS[k]` держит прошлый
статус, `setCell` для них не вызывается, зелень остаётся. Плюс
`$("field").dataset.built` не даёт перестроить поле.

**Почему не заметили раньше.** Один прогон за запуск стека. Дефект вылезает
только со второго `mission-rerun`, а этот таргет появился 2026-07-27.

**Обход прямо сейчас.** Перезагрузить страницу (F5) после рестарта миссии.

**Как чинить по-настоящему.** Фронт должен заметить смену прогона и обнулить
локальное состояние: в `state/current_run.json` есть `run_id`. При изменении
`run_id` — очистить `CELLS`, снять `dataset.built`, перестроить поле. Пока не
сделано.

## Подтверждённый дефект 2: `reset_runtime()` чистит по белому списку

`bb.py:75` удаляет ровно перечисленные файлы состояния:

```python
for name in ("phase", "decision", "assignments", "world", "collaborative",
             "current_run", "pause"):
```

Любой новый файл в `state/` переживёт сброс молча. Это уже происходит:
`state/commerce_cursor.json` (его пишет `payments/blackboard_bridge.py`) не
входит в список и тащится из прогона в прогон. Для курсора это, возможно, и
задумано, но нигде не записано, а значит следующий, кто добавит файл
состояния, наступит на те же грабли.

Правильнее — чистить всё, кроме явного списка исключений (инверсия), либо
завести реестр «переживает сброс».

## Что не проверено вообще

- Конкурентная запись с нескольких хостов (`HttpBoard`, режим distributed):
  атомарность `read_json`/`write_json` под параллельной нагрузкой не
  нагружалась. Один прогон 4 дрона + ровер проходит, гонок не искали.
- Поведение при заполненном диске / `OSError` — исключения глотаются
  (`except OSError: pass` в `reset_runtime`), сброс может пройти частично и
  промолчать.
- `keep_registry=False` — ветка не покрыта тестами.
- Восстановление после обрыва: половина сообщения записана, `.seq` уехал.

## Что проверено и работает

- Одиночный прогон survey/city, 4 дрона + ровер, `FileBoard` — стабильно.
- Distributed-прогон через `HttpBoard` (хаб по HTTP) — PASS, дроны и ровер
  регистрируются, миссия доходит до DONE.
- `agent/binding.py` — покрыт тестами (см. `docs/fleet.md`).
