# `rover/` — всё про командный ровер

Одна папка на весь ровер: программа, которой диспетчер им командует, проверка перед
попыткой, снятые с борта SLAM-карты. Справочная документация по роверу здесь **не**
лежит — она в `docs/rover/` (выжимка апстрима `sverk_rover`), потому что `docs/` в
этом репозитории отведён только под документацию.

| Файл | Что это | Где ещё описано |
|---|---|---|
| `rover_agent.py` | агент ровера: наш HTTP-контракт `/status /drive /led /stop /fire`, переводчик клеток поля в метры карты | `PLAN.md` этап 4, `RUN.md` 3Б |
| `check_rover.py` | прогон агента по HTTP: контракт, лента, отказы, движение, железо | ниже на этой странице |
| `maps/` | SLAM-карты, снятые с живого ровера (`карта.*`, `тест.*`): `.pgm` + `.yaml` для Nav2, `.json` + `.png` — как их отдаёт веб | `RUN.md` 3Б.4 |
| `fix1.py` | одноразовый диагностический скрипт по топикам ровера через `rover_web`, писался под конкретную сверку | — |

Всё только на стандартной библиотеке, запускать из корня репозитория. Тесты агента
лежат отдельно, в общей папке `tests/test_rover_agent.py`, — чтобы один прогон
`python3 -m unittest discover -s tests` по-прежнему покрывал весь репозиторий.

## `rover_agent.py` — агент ровера

В отличие от дрона **не копируется на борт**: у ровера уже есть свой сетевой API
(`rover_control_api :8767` — движение, `rover_web :8765` — лента), поэтому агент
запускается там, откуда видно ровер, — с ноутбука рядом с диспетчером:

```bash
python3 rover/rover_agent.py --port 8010 --rover-ip АДРЕС
```

Порядок запуска, ключи и калибровка привязки сетки (`--map-x0/--map-y0/--map-yaw`) —
`RUN.md` пункт 3Б. В зачётной попытке ровером командует диспетчер
(`python3 -m city.run`) через этот агент.

### Квадрат огня: `POST /fire` и `GET /fire`

Диспетчер сообщает роверу, **где горит**, — сразу после разведки и ещё раз, когда
посчитает клетку подъезда. Это **знание, а не команда движения**: ровер квадрат
запоминает, отдаёт в `/status` и в `GET /fire`, но никуда по нему не едет. Ехать по
нему нельзя до калибровки сетки (`--map-x0/--map-y0/--map-yaw`), иначе любая будущая
маршрутизация уедет не туда, и запрет въезда в горящую клетку по-прежнему держит
диспетчер, а не ровер.

```bash
curl -X POST http://127.0.0.1:8010/fire -d '{"cell":[4,2],"level":3,"tower":[1,3]}'
curl http://127.0.0.1:8010/fire        # {"known":true,"fire":{…}}
curl -X POST http://127.0.0.1:8010/fire -d '{"clear":true}'   # потушено — забыть
```

Каналов доставки два, и второй нужен именно потому, что агента запускают руками:

| Канал | Как | Зачем |
|---|---|---|
| `POST /fire` | основной | приходит **до** первого переезда, умеет `clear`, отвечает кодами (400 без `cell`, 403 за полем) |
| поля `fire`/`fire_level` в теле `POST /drive` | резервный | агент любой версии лишние поля тела молча игнорирует, поэтому 404 на этом пути **невозможен по построению** |

Откуда квадрат приехал, видно в `/status` полем `via` (`fire` или `drive`). Время
диспетчера кладётся отдельным полем `at_dispatcher` и с местными часами не
сравнивается — возраст ровер считает сам полем `since`. Незнакомые ключи не
выбрасываются, а складываются в `extra`: диспетчер может поумнеть раньше агента.
`/fire` не берёт замок движения, поэтому 409 «занят» на нём не бывает — квадрат можно
уточнить посреди заезда.

## `check_rover.py` — прогон агента ровера

Проверка того, что сделано на этапе 4 (`rover/rover_agent.py`): скрипт стучится в
HTTP-контракт агента и печатает по строке на каждую проверку. Один файл, только
стандартная библиотека, никаких симуляций — просто список запросов и ответов. В
зачётной попытке не участвует, это проверка перед ней.

Это **не** замена `tests/test_rover_agent.py` (те гоняют внутренности на заглушке
бэкенда). Здесь проверяется агент целиком, живым HTTP, включая тот случай, когда за
ним стоит настоящий ровер.

## Как запускать

**Без ровера, «сам себе стенд»** — скрипт поднимает `rover_agent.py --dry` на порту
8019, гоняет всё, включая переезд, и глушит агента:

```bash
python3 rover/check_rover.py
```

**По уже запущенному агенту** (тому, что смотрит на живой ровер, см. `RUN.md` 3Б).
Движение по умолчанию пропускается — ровер поедет по-настоящему:

```bash
python3 rover/check_rover.py --url http://127.0.0.1:8010
python3 rover/check_rover.py --url http://127.0.0.1:8010 --move
```

**Плюс железо мимо агента** — два GET прямо в родные API ровера, чтобы отделить
«агент виноват» от «ровер молчит»:

```bash
python3 rover/check_rover.py --url http://127.0.0.1:8010 --rover-ip 192.168.1.125
```

Код возврата 0 — всё прошло, 1 — есть провалы. На этой машине запускать полным путём
и с `PYTHONIOENCODING=utf-8` (см. `CLAUDE.md`).

## Что проверяется

| Раздел | Проверки |
|---|---|
| Контракт | `/status` отвечает 200 и содержит все поля (`ok role state cell since_move busy led`), роль `rover`, клетка — пара целых, чужой путь → 404 |
| Лента | `blink`, `on`, `off` — каждый режим отражается в `/status`; неизвестный режим → 403 |
| Отказы | несоседняя клетка → 403, `/drive` без `cell` → 400 |
| Движение | переезд в соседнюю клетку, подтверждение по `cell` и `state=idle`, дедуп повторного `command_id`, возврат в исходную клетку |
| Квадрат огня | `POST /fire` принят и виден в `/status` и `GET /fire`; время диспетчера лежит отдельно от своего; без `cell` → 400; за полем → 403; дедуп по `command_id`; **резервный канал** — квадрат в теле `/drive` доезжает и помечается `via:"drive"`; `clear` забывает |
| Стоп | `/stop` → `state=stopped` (последней проверкой, чтобы оставить ровер стоящим) |
| Железо | `rover_control_api :8767` отвечает, `nav2_ready`, фрейм позы, метка карты; `rover_web :8765` отвечает |

## Что НЕ проверяется

- **Сторож (watchdog)** — требует 3+ секунды тишины при едущем ровере, на заглушке
  переезд мгновенный. Проверяется на площадке глазами: закрыть диспетчер на ходу.
- **409 «занят»** — на заглушке команда успевает отработать раньше, чем придёт вторая.
- **Точность заезда и калибровка сетки** — это не про контракт, а про `--map-x0/--map-y0/--map-yaw`,
  процедура в `RUN.md` 3Б.4.

Раздел «Квадрат огня» при этом работает и **без Nav2**: это знание, а не движение.
Значит первый день на площадке закрывает эту часть цепочки «дрон → диспетчер → ровер»
раньше, чем поднимут навигацию.

## Что сейчас показывает живой ровер (29.07.2026)

На `192.168.1.125` прогон даёт единственный провал, и он **ожидаемый**:

```
[ПРОВАЛ] Nav2 поднят — nav2_ready=False, поза во frame 'odom'
```

Оба порта живы, лента слушается, агент отвечает; Nav2 просто не запущен, и агент
поэтому честно отказывается ехать. Поднятие Nav2 — задача первого дня; после неё эта
строка должна стать `ОК`, и только тогда имеет смысл гонять `--move` на железе.
