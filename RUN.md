# Памятка на площадку

Что запускать, в каком порядке, что должно появиться на экране и что делать, если
пошло не так. Пишется заранее — в день зачёта читать документацию некогда.

Сейчас закрыты этапы 0–3: мозг диспетчера, связь по сети, программа для дрона-монитора и
зрение — дрон облетает свой угол поля и сам находит очаг на кадре.
Ровер и микродрон сюда добавятся, когда до них дойдёт очередь.

---

## 1. Запуск — одна команда

```bash
cd ~/Desktop/gorod_dronov && python3 -m city.run --sim
```

Это главная команда: она проигрывает зачётную попытку целиком. Железо не нужно —
ни дрона, ни ровера, ни поля. Делается перед любым выездом: если команда прошла,
программа цела.

### Что будет, если её запустить

За секунду на экране появится вся попытка, строка за строкой. Каждая строка — событие
и объяснение по-русски, зачем оно. По порядку:

- `RUN_START` — начало попытки, поле 6×6 и какие подсистемы включены;
- `SURVEY` — откуда взята обстановка (без дронов — из настроек `city/config.yaml`);
- `PLAN_CHOSEN` — что решил диспетчер и почему: миссия «Пожар», клетка очага, уровень
  (сколько раз ехать за водой), с какой соседней клетки тушим;
- `CHARGED` — сколько секунд ровер стоит на зарядке и откуда взялось это число;
- дальше пары «`DWELL` три секунды у башни → `MOVE` к горящему дому» — по одной паре
  на каждый цикл подвоза воды, с остатком игрового заряда в конце каждой строки;
- `FIRE_EXTINGUISHED` — пожар потушен, и `DONE` — попытка закончена;
- последняя строка — путь к файлу лога вида `logs/run-20260728-141247.jsonl`.
  Это и есть тот самый лог решений, которого требует регламент.

Миссия в логе одна: «Доставку» команда не выполняет (PLAN.md).

Ничего не летает и не едет — время внутри программы виртуальное. Чтобы то же самое
пошло на настоящем дроне, нужен пульт (пункт 3.3) и прогон по сети (пункт 3.10).

## 2. Проверка связи без железа

Три окна терминала. В первых двух — «понарошечные» робот и дрон, в третьем — диспетчер.

```bash
# окно 1
python3 -m city.robots.mock_server --role rover --port 8010
# окно 2
python3 -m city.robots.mock_server --role drone --port 8020 --cell 1,1 --name m1
# окно 3
python3 -m city.run --net --drones --monitors m1
```

Это тот же прогон, что в пункте 1, но команды идут по сети и в реальном времени
(полторы-две минуты). Если он проходит — сеть, ожидания и проверки в порядке, и на
железе останется только заменить адреса.

Понарошечный дрон при этом отдаёт не пустую картинку, а нарисованное поле с метками и
очагом, так что по сети проверяется и зрение целиком. Ключ `--blank` возвращает пустой
кадр, если нужно проверить только связь.

## 3. Дрон-монитор: первый запуск

### 3.1. Безопасность — до того, как подключать батарею

- [ ] Пропеллеры ставятся **последними**, перед самым взлётом. Все настройки и
      проверки — без пропеллеров.
- [ ] Пульт включён и в руках у человека, который **не** сидит за ноутбуком.
      Аварийное отключение (KILL SWITCH) — тумблер SD.
- [ ] В полётной зоне никого.
- [ ] Батарея заряжена: регламент требует не меньше 40 %. Для 3S LiHV полный заряд
      13,05 В, в полёте не опускаться ниже 10,65 В.
- [ ] Порядок включения: сначала пульт, потом батарея дрона. Выключение — наоборот.

### 3.2. Узнать адрес дрона

Дрон — это маленький компьютер в сети. Нужен его адрес вида `192.168.1.50`.
Способы, по убыванию удобства:

1. Спросить у того, кто настраивал сеть (на площадке — у организаторов).
2. Открыть в браузере веб-интерфейс дрона — если он открывается, адрес в строке браузера.
3. Проверить, что адрес рабочий: `ping 192.168.1.50` — должны идти ответы.

Дальше в командах вместо `АДРЕС` подставляйте этот адрес.

### 3.3. Пульт — одна команда вместо трёх окон

Обычный способ работы. Всё, что расписано дальше в пунктах 3.4–3.7, эта команда делает
сама: кладёт на дрон свежую программу, запускает её, зовёт её по сети и показывает
сообщения борта. Пункты 3.4–3.7 нужны, только если пульт почему-то не пошёл.

```bash
python3 -m city.pult
```

Через полминуты в том же окне:

```
[10:55:01] дрон 192.168.1.105: проверяю связь
[10:55:02] программа на борту обновлена
[10:55:02] запускаю программу на борту (ROS поднимается небыстро, это нормально)
  борт | [07:55:01] дрон на связи, камера готова (цвет: bgr)
  борт | [07:55:01] агент «m1» слушает порт 8020
[10:55:02] зову борт: http://192.168.1.105:2200
[10:55:02] готово. Дрон ждёт команд
[10:55:02] стоит на земле, высота 0.0 м, клетка [1, 1], камера готова
команда>
```

Дальше просто печатаете команды в это же окно:

| Команда | Что делает |
|---|---|
| `статус` | что с дроном сейчас |
| `кадр` | снять фотографию, сохранить и открыть её |
| `взлет` | подняться на 1,5 м (`взлет 1.2` — на другую высоту) |
| `обзор 0.5` | облёт: по очереди на 0,5 м в восемь сторон, каждый раз кадр и возврат на метку |
| `обзор 0.5 0.5` | одна точка: отлететь от метки на столько метров по каждой оси, снять кадр, вернуться |
| `сесть` | посадка |
| `стоп` | аварийная посадка немедленно |
| `выход` | посадить, всё выключить и выйти |

Хватает и первой буквы: `с`, `к`, `в`, `о`, `п`.

Перед первым за запуск взлётом пульт покажет предполётный список и попросит напечатать
«да» — это защита от случайного взлёта, а не формальность.

Сообщения борта («ВЗЛЁТ», «вишу», «ПОСАДКА», «СТОРОЖ») приходят в это же окно с пометкой
`борт |`, так что второе окно не нужно.

Выход по `выход` или `Ctrl+C` **сажает дрон, если он в воздухе** и останавливает
программу на борту. Другой дрон — `python3 -m city.pult --ip 192.168.1.107
--name m2 --cell 4,1`.

### 3.4. Положить программу на дрон

Один раз на новом дроне — вход без пароля (пароль спросит только сейчас, дальше никогда):

```bash
ssh-copy-id -i ~/.ssh/id_ed25519_1schedule.pub sverk@АДРЕС    # пароль: sverk
```

Копируем обе программы — саму бортовую и пусковой скрипт к ней:

```bash
ssh sverk@АДРЕС 'mkdir -p ~/gorod_dronov/onboard'
scp onboard/drone_agent.py onboard/run_agent.sh sverk@АДРЕС:~/gorod_dronov/onboard/
ssh sverk@АДРЕС 'chmod +x ~/gorod_dronov/onboard/run_agent.sh'
```

Зайти на дрон: `ssh sverk@АДРЕС`. Вы окажетесь **внутри контейнера** — это то, что нужно.

### 3.5. Запустить

На дроне (в том окне, где вы по `ssh`):

```bash
cd ~/gorod_dronov && ./onboard/run_agent.sh --name m1 --cell 1,1
```

**Запускать только через `run_agent.sh`.** Просто `python3 drone_agent.py` на борту не
работает: системному питону сломали `cv2` (поверх старого numpy доставили новый), а
`sverk_interfaces` виден только после двух команд `source`. Скрипт делает и то, и другое.

Должно появиться:

```
[12:30:01] подключаюсь к дрону…
[12:30:03] дрон на связи, камера готова (цвет: bgr)
[12:30:03] агент «m1» слушает порт 8020
```

**Строка «камера НЕ ГОТОВА» — это сразу стоп.** Кадров не будет, а без кадров дрон-монитор
бесполезен. Не взлетайте, разбирайтесь с камерой.

Окно с этой программой должно оставаться открытым. Закроете — дрон перестанет принимать
команды (и, если он в воздухе, сядет сам через 20 секунд).

Остановить: `Ctrl+C` в этом окне. Если программа осталась работать с прошлого раза
(при запуске пишет `ПОРТ 8020 УЖЕ ЗАНЯТ`), убить её с ноутбука:

```bash
ssh sverk@АДРЕС 'pgrep -af "[d]rone_agent"'      # посмотреть, что запущено
ssh sverk@АДРЕС 'pkill -9 -f "[d]rone_agent"'    # остановить
```

Квадратные скобки — не опечатка и не украшение: без них команда находит саму себя и
обрывает соединение раньше, чем доберётся до агента. И именно `-9`: обычный `kill`
эту программу не берёт.

### 3.6. Два номера порта — не перепутать

Программа на борту сидит **внутри контейнера** и слушает порт **8020**. Снаружи этот порт
виден под другим номером — **2200**. Так настроено на всех дронах и сохраняется после
перезагрузки.

Отсюда правило: на дроне — 8020, с ноутбука и с других дронов — **2200**.

```bash
curl http://АДРЕС:2200/status      # так дрон зовут снаружи
```

Ничего запускать и держать открытым для этого не надо. Если ответа нет, а на самом дроне
(`curl http://127.0.0.1:8020/status` в окне `ssh`) всё отвечает — значит на этом борте
проброс не настроен, спрашивайте того, кто настраивал дрон.

### 3.7. Проверить с ноутбука — сначала на земле

```bash
curl http://АДРЕС:2200/status
```

Ответ должен содержать `"state": "idle"` и `"camera": true`.

Кадр **без взлёта** — самая ценная проверка, делайте её обязательно:

```bash
curl http://АДРЕС:2200/shot -o kadr.jpg
open kadr.jpg
```

Открылась фотография пола — камера, сеть и сжатие работают. Дальше можно летать.

Отдельно посмотрите на **цвета** — но сверяйтесь с предметом, цвет которого точно знаете
(лента, коробка, ваша куртка), а не «на глаз по полу»: пол в помещении сам может быть
синим, и тогда правильный кадр выглядит подозрительно. Если красное в кадре выходит синим,
а синее красным — перезапустите программу с `--color rgb`. На наших дронах проверено:
правильно `--color bgr`, это и стоит по умолчанию.

### 3.8. Первый полёт

Пропеллеры на месте, пульт РУ в руках у второго человека, зона пустая.

В пульте (пункт 3.3) это четыре слова подряд:

```
команда> взлет          → пульт покажет список и спросит «да»
команда> статус         → должно быть «висит, высота 1.5 м»
команда> кадр           → снимок с высоты откроется на экране
команда> сесть          → «дрон сел»
```

Тем же в обход пульта, если он не пошёл:

```bash
curl -X POST http://АДРЕС:2200/takeoff -d '{"alt":1.5}'   # взлёт на 1,5 м
curl http://АДРЕС:2200/status                              # ждём "state": "hover"
curl http://АДРЕС:2200/shot -o pole.jpg                    # кадр с высоты
curl -X POST http://АДРЕС:2200/land                        # посадка
```

Дрон отчитывается о каждом шаге: `ВЗЛЁТ на 1.5 м`, `вишу на 1.5 м`, `ПОСАДКА`.

### 3.9. Проверить сторожа (тоже полёт)

Взлететь и **ничего не делать 25 секунд** (в пульте — просто не печатать). Дрон должен
сесть сам, а на экране появится `СТОРОЖ: 20 с без команд с ноутбука — сажусь сам`. Это
требование регламента про отключение при потере связи, и это же спасёт аппарат, если
ноутбук зависнет.

### 3.10. Полёт под управлением диспетчера

Это уже вся система целиком, а не ручные команды.

Оставьте пульт открытым — он держит программу на борту. Во **втором окне**:

```bash
python3 -m city.run --net --drones --monitors m1 --drone-url http://АДРЕС:2200
```

**Пока идёт прогон, в пульт ничего не печатайте** — двое командующих одним дроном ни к
чему хорошему не приведут. Пульт в это время работает окном отчёта: строки борта видны там.

Дрон взлетит, снимет кадр, сядет; кадр окажется в `logs/shots/`, а в логе появится строка
`ROBOT` с адресом настоящего дрона.

### 3.11. Настроить зрение (нужен один полёт и рулетка)

Пока это не сделано, диспетчер очаг не найдёт: пороги в `city/config.yaml` — гипотезы,
а не замеры. Всё правится в одном файле, перезапускать ничего не нужно.

1. **Угол обзора камеры.** Положите на пол предмет известной длины (метровую рейку),
   поднимите дрон на 1,5 м, снимите кадр. Посмотрите, какую долю ширины кадра занял
   предмет: если метровая рейка заняла половину ширины — в кадр влезает 2 м, и
   `camera.fov_deg` считается как `2 * atan(1 / 1.5) ≈ 67°`. Достаточно попасть в
   пять градусов.
2. **Цвет «огонька» — уже замерен, нужно только подтвердить.** Пороги в настройках
   посчитаны по восьми фотографиям настоящего жетона (`photo_fire/`, 28 июля): он
   тёмно-красный, а не оранжевый, и отличается от розового района поля насыщенностью.
   На площадке снимите кадр командой `кадр` в пульте — она сразу разбирает снимок и
   говорит, нашёлся ли очаг, в какой клетке и **сколько в нём огоньков**, а рядом кладёт
   файл `*-mark.jpg`, где обведён каждый жетон. Свет в зале другой, поэтому если жетон не
   нашёлся — снижайте нижнюю границу насыщенности (третье число, сейчас 120) в
   `vision.fire_hsv`. Если вместо жетона отмечен район поля — наоборот, поднимайте её.
3. **Как разложены огоньки — от этого зависит уровень пожара.** Сколько жетонов лежит
   рядом, столько раз ровер поедет за водой, поэтому на размеченном кадре пересчитайте
   обведённые кружки и сверьте с тем, что видно глазами. Если жетоны разложены просторнее
   40 см и кучка распалась на две — увеличьте `vision.fire_group_m`. Если один жетон
   посчитан за два, а расчётов по площади вы не ждали (в логе `count_source: area`) —
   проверьте `camera.fov_deg`: этот путь ошибается, когда завышен масштаб кадра.
4. **Поворот метки.** Если клетка на разметке повёрнута относительно настоящей
   (очаг «уехал» в зеркальную клетку), поставьте `vision.marker_edge_deg` 90, 180 или 270
   и снимите кадр снова. Проверяется один раз и на всё соревнование.
5. **Удержание курса.** Борт держит курс по своей метке: после взлёта он запоминает,
   как метка повёрнута в кадре, и дальше подмешивает доворот в каждый перелёт, а на
   долгом висении доворачивает отдельно (`navigate` с `yaw=0.0` курс НЕ держит).
   Проверяется на глаз: после взлёта команда `статус` должна сказать `курс: увод +N°`
   с небольшим N, а дрон за минуту висения не должен заметно развернуться. Строка
   `курс: держать нечем` над своей меткой означает, что метку в кадре не видят —
   разбираться с камерой и высотой. Выключается ключом пульта `--no-yaw-hold`;
   с `--frame aruco_map` не работает вовсе (там курс держит бортовая локализация).
6. **Удержание высоты над разновысотным полем.** Дальномер дрона меряет расстояние
   до того, что под ним ПРЯМО СЕЙЧАС, а площадки стоят на крышах домиков (0,52 и
   0,83 м). Крыша — одна клетка 80×80 см, то есть от метки до края 40 см, а точки
   обзора отстоят на 50 см: за край дрон вылетает обязательно. Замер скачком растёт
   на высоту дома, автопилот принимает это за собственный подъём и **проседает**;
   на возврате — подскакивает. Борт теперь переносит скачок в цель: замер вырос на
   полметра — значит и просит он на полметра больше, автопилоту нечего исправлять.
   Делается это немедленно и во время перелёта тоже (раньше корректор на время
   команды засыпал — то есть спал ровно тогда, когда край и пересекается).
   Проверяется командой `статус`: поле `над полем` (`agl`) должно оставаться
   примерно одинаковым, когда дрон отлетает с крыши на поле и обратно, а поле
   `под дроном` (`ground`) — меняться на высоту дома. Если ступеньки не ловятся
   вовсе (`ступенек: 0` при явном перелёте через край) — уменьшайте порог ключом
   борта `--terrain-step`. Высота своей площадки берётся из карты поля по клетке;
   **перемерьте её рулеткой** и задайте ключом борта `--pad-z`, если карта врёт:
   на неё завязана проверка «уровень поверхности похож на настоящий».
   Выключается ключом пульта `--no-alt-hold`.
   **На железе не проверялось ни разу** — это первое, что стоит посмотреть в полёте.
   Перед первым полётом стоит убедиться, что дальномер вообще отвечает: в `статусе`
   должны быть поля `над полем` и `под дроном`, а не `ВЫСОТУ НЕ ДЕРЖУ`.
7. **Облёт.** Команда `обзор 0.5` в пульте: дрон по очереди отлетит на полметра в восемь
   сторон (вперёд, наискосок, вбок и так далее), на каждой точке снимет кадр и вернётся
   на метку — всего шестнадцать перелётов, примерно две-три минуты. Кадры складываются в
   `logs/shots/` и на экран не открываются: смотреть в это время надо на дрон. Разобрать
   их можно после посадки — по ним видно, сколько поля влезает в кадр с точки обзора, а
   от этого зависит список точек в `survey.offsets`. Форма `обзор 0.5 0.5` осталась: это
   одна точка, кадр с неё открывается сразу. Дальше метра от своей метки борт не
   улетит — пульт откажет и объяснит; предел меняется ключом пульта `--scan-radius`.
   Наискосок дрон летит те же полметра (по каждой оси выходит по 0,35 м), а не полметра
   по каждой оси, — иначе угловые точки уехали бы за предел.

## 4. Строка на экране → что случилось → что делать

| Строка | Что это значит | Что делать |
|---|---|---|
| `камера НЕ ГОТОВА` | нет библиотек или патча камеры | не летать, разбираться с камерой |
| `нет входа по ssh` | ключ на этот дрон не залит | одна строка из пункта 3.4 |
| `борт не отозвался за 40 с` | дрон выключен, не в сети или ROS не поднялся | `ping`, питание, подождать и повторить |
| `ПОРТ 8020 УЖЕ ЗАНЯТ` | программа на дроне уже запущена | пульт решает сам; вручную — пункт 3.5 |
| `ModuleNotFoundError: sverk_interfaces` | запустили не через `run_agent.sh` | запускать скриптом |
| красное в кадре синее | камера отдаёт цвета наоборот | перезапустить с `--color rgb` |
| с ноутбука нет ответа, с дрона есть | на этом борте нет проброса 2200 | пункт 3.6, спросить того, кто настраивал дрон |
| `ROBOT … нет связи` | борт не ответил диспетчеру | проверить адрес и `ping`, включён ли дрон |
| `ВНИМАНИЕ: на том конце программа-заглушка` | дрон запущен с `--dry` | перезапустить без `--dry`, этот прогон не считается |
| `409 занят` | пришла вторая команда, пока идёт первая | это защита, а не поломка: дождаться конца |
| `взлёт не принят` | дрон не встал в OFFBOARD или не заармился | проверить пульт, `selfcheck`, батарею |
| `ПОСАДКА НЕ ПОДТВЕРЖДЕНА` | команда посадки не сработала | **сажать пультом**, дальше не командовать |
| `СТОРОЖ: … сажусь сам` | нет команд с ноутбука | норма при обрыве; проверить сеть |
| `SCAN … очага на кадре нет` | зрение не нашло «огонёк» | нормально для дальнего угла; если так на всех кадрах — пункт 3.11 |
| `SURVEY … очаг ни на одном не распознан` | облёт прошёл, находки нет | работаем по клетке из настроек; пороги цвета — пункт 3.11 |
| `курс: увод +12°, доворачиваю` | борт заметил разворот и отрабатывает его | норма, вмешиваться не нужно |
| `курс: держать нечем — метки не видно` | метки своей площадки нет в кадре | над меткой — разбираться с камерой; на точке обзора это норма |
| `курс: поворот метки больше 45°` | сбой опознания метки, а не разворот дрона | борт сам игнорирует такой замер; если строка идёт подряд — свет и резкость кадра |
| `под дроном провал 0.50 м … высоту не меняю` | дрон вышел за край дома, дальномер это заметил | норма, ради этого всё и сделано: дрон остаётся на прежней высоте над полем |
| `высота: … не ложится ни на один известный уровень` | замер не похож ни на крышу, ни на пол | борт ловит скачки, но дрейф не правит; если строка держится — перемерить площадку и задать `--pad-z` |
| `высота: ушёл на +0.20 м — возвращаю` | дрон сам всплыл или просел | норма; если строка идёт каждые несколько секунд — дрон плохо держит высоту, смотреть на ветер и заряд |
| `ВЫСОТУ НЕ ДЕРЖУ: дальномер молчит` | замера высоты нет | полёт продолжается, но высота на автопилоте; после посадки — проверить, поднят ли дальномер |
| `ВЫСОТУ НЕ ДЕРЖУ: на этой сборке нет команды set_altitude` | старая бортовая нода | летать с `--no-alt-hold`, высоту держать глазами |
| `облёт запрещён` | борт запущен без `--allow-scan` | перезапустить пультом: он ставит ключ сам |
| `точка … от своей метки, предел 1 м` | диспетчер послал дрон слишком далеко | так и задумано; проверить `survey.offsets` |
| `DWELL … НЕ ЗАСЧИТАНО` | стоянка не засчитана по регламенту | смотреть на `moved` и `led` в той же строке |
| `ENERGY_BLOCK` | у ровера кончился игровой заряд | ошибка расчёта бюджета, смотреть строку `CHARGED` |

## 5. Аварийная остановка

По убыванию скорости:

1. **KILL SWITCH на пульте РУ** (тумблер SD) — мгновенно и всегда. Дрон падает, зато
   никого не порежет.
2. Слово `стоп` в пульте — дрон садится сам. Одна буква и Enter, руки уже на клавиатуре.
3. `Ctrl+C` в пульте — сажает дрон и всё выключает.
4. `Ctrl+C` в окне диспетчера — диспетчер глушит все аппараты.
5. Без пульта: `curl -X POST http://АДРЕС:2200/stop`.
6. Совсем крайнее: `ssh sverk@АДРЕС 'pkill -9 -f "[d]rone_agent"'` — программа на борту
   умирает, и дрон садится сам через 20 секунд по сторожу.

## 8. Тесты

Нужны, только если что-то правили в коде. Железо не требуется, обе команды — из папки
`~/Desktop/gorod_dronov`.

```bash
python3 -m unittest discover -s tests      # все проверки разом, должно закончиться словом OK
```

Около 45 секунд, 178 проверок (одна пропускается — это норма). Последняя строка `OK` — всё цело. `FAILED` — что-то сломано,
на площадку с этим не выезжать.

```bash
python3 -m city.run --sim --drones --sim-fire-cell 1,2    # очаг перенесли — план идёт за ним
python3 -m city.run --sim --drones --sim-fire-count 3     # три огонька — три поездки за водой
```

Проверка зрения на нарисованном поле: дрон «облетает» свой угол, сам находит очаг, и в
логе появляется строка `FIRE_SPOTTED` с клеткой `[1, 2]`, числом согласных дронов и
числом огоньков — дальше план строится по ним, а не по настройкам. Во второй команде на
поле лежит три жетона, хотя в настройках записан уровень 2: в логе будет
`огоньков=3 уровень=3 (frames)` и три цикла подвоза воды. Если вместо клетки подставить
`--sim-fire-cell нет`, строки `FIRE_SPOTTED` не будет вовсе, а `SURVEY` честно скажет,
что очаг не распознан. Это и есть главная проверка: система не выдумывает того,
чего не видела.
