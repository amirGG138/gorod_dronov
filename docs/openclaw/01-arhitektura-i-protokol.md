# Архитектура и протокол координации

Источники: `snapshot/agent-coordination-spec.md`, `snapshot/BUILD_BRIEF.md`,
`snapshot/docs/architecture.md`, `snapshot/docs/protocol.md`, `snapshot/docs/bridge.md`.

## Основная идея

> Общая папка сама по себе **не** порождает сотрудничество — агенты генерируют
> параллельно и говорят мимо друг друга.

Из этого выведены две конструкции: **фазовая машина** (кто когда имеет право
говорить) и **novelty gate** (фильтр повторов). Всё остальное — обвязка.

Три подсистемы, слабо связанные между собой:

```
агенты (agent/)  ──пишут──▶  доска (blackboard)  ──читает──▶  дашборд (viz/)
     │
     └──HTTP──▶ бридж (bridge/) ──▶ робот: мок | Gazebo | железо
```

Агент **никогда не импортирует ROS 2**. Он ходит в бридж по HTTP. Это и есть
шов «симуляция ↔ железо»: у мока, у Gazebo-моста и у боевой ноды один и тот же
HTTP-контракт, поэтому переезд на борт не меняет ни строчки в агентах.

## Доска (blackboard)

Файловая структура, строгое правило единственного писателя:

```
blackboard/
  task.md                 # цель (координатор пишет на INIT)
  config.yaml.json        # снимок конфига прогона
  agents/<id>/meta.json   # реестр подключённых — на этом строится discovery
  .seq                    # глобальный монотонный счётчик, под flock
  messages/<seq>-<ts>-<id>-<type>.json   # append-only, seq в начале имени
  state/
    phase.json            # писатель: координатор
    decision.json         # писатель: координатор
    assignments.json      # писатель: координатор
    world.json            # писатель: координатор
    progress/<id>.json    # писатель: только сам агент
    pause.json            # писатель: оператор (пауза, замена АКБ)
  artifacts/              # снимки, скопированные бриджем
  events.jsonl            # append-only лента для дашборда
```

Почему это гоночно-безопасно:

- каждый файл состояния имеет ровно одного писателя (прогресс разнесён по
  файлам на агента — строже, чем в исходной спеке);
- у каждого сообщения есть глобальный монотонный `seq` из flock-защищённого
  `.seq`; потребители сортируют по `seq`, **а не по `ts`** — порядок переживает
  расхождение часов между бортами;
- строки `events.jsonl` короче `PIPE_BUF` (4096 Б) и пишутся одним `O_APPEND` →
  атомарная конкурентная дозапись на Linux;
- записи JSON-состояния атомарны (временный файл + `os.replace`).

Две реализации за одним интерфейсом (`agent/bb.py`):

- **`FileBoard`** — каталог/том, для агентов на одной машине;
- **`HttpBoard`** — те же методы, но каждое чтение/запись идёт в центральный
  **hub** по HTTP; чтения терпимы к обрыву (возвращают дефолты), записи —
  best-effort.

`make_board(agent_id)` выбирает `HttpBoard`, если задан `HUB_URL`. Роли не
знают, с какой из них работают. Именно это позволяет разнести дронов по
отдельным Pi без правки логики.

## Фазовая машина

Базовая (из спеки):

```
INIT ──▶ PROPOSE ──▶ CONVERGE ──▶ EXECUTE ──▶ REPORT ──▶ DONE
                         ▲                        │
                         └──────── reopen ◀───────┘
```

По умолчанию вместо тихого PROPOSE/CONVERGE включён **открытый чат**
(`SCOUT_CHAT=1`): `INIT ─▶ CHAT ─▶ EXECUTE ─▶ REPORT ─▶ DONE`. В CHAT дроны
торгуются за сектора вслух (claim / argue / trade / done), координатор выводит
`assignments` из последнего заявления каждого. Конфликты — побеждает тот, кто
договорился раньше; остатки раздаются по кругу.

У сценария города своя, более короткая машина
(`agent/roles/city_missions.py`): `INIT ─▶ SURVEY ─▶ EXECUTE ─▶ DONE`.

Дедлайны фаз (`agent/loop.py`, `build_config`): propose 25 с, converge 25 с,
execute 120 с, report 120 с. Дедлайн — единственная защита от зависшего агента,
который иначе блокирует весь прогон.

**Ворота ровера** — ключевая зависимость. В EXECUTE задание ровера равно
`{"wait_for": "world.ready"}`; он публикует `BLOCK` и стоит. В REPORT
координатор сводит снимки в `world.json`, и когда `gaps == []` и все препятствия
локализованы — ставит `ready = true`. Только это разблокирует движение.

## Сообщения

Один JSON-файл на сообщение, имя `{seq:06d}-{ts}-{from}-{type}.json`.

```json
{
  "id": "msg-drone-2-0007", "seq": 7,
  "from": "drone-2", "to": "all", "phase": "PROPOSE", "type": "PROPOSAL",
  "ts": "...", "ref": null, "novelty": 0.81,
  "body": "текст для человека",
  "payload": { "scheme": "length-4", "claim_sector": "A" }
}
```

`body` — для человека, `payload` — машинно-исполняемая часть. Типы:
`PROPOSAL`, `VOTE`, `ASSIGNMENT`, `STATUS`, `REPORT`, `BLOCK`, `CHAT`, `PLAN`,
`FOUND`, `VERIFY`; в городском сценарии добавлены `CLAIM`, `OBSERVATION`,
`FACILITATE`, `DECISION`.

## Novelty gate

Перед публикацией сообщение оценивается на прирост информации относительно
доски: `novelty = 1 − max_similarity` (Jaccard по токенам, `agent/bb.py`).

- **Свободная болтовня** (`PROPOSAL`) ниже `NOVELTY_MIN` (по умолчанию 0,3)
  **не публикуется** — пишется событие `drop`. Это лечит режим отказа, когда
  две трети реплик роя повторяют уже сказанное.
- **Протокольно-критичные** (`VOTE`, `ASSIGNMENT`, `STATUS`, `REPORT`, `BLOCK`)
  публикуются всегда, но оценка всё равно считается — для дашборда.

Разделение живёт в `agent/loop.py`: `gated_types = {"PROPOSAL"}`.

## Цикл агента

```python
while True:
    phase = read("state/phase.json")["phase"]
    if phase == "DONE": break
    result = role.step(ctx)               # поведение роли для (role, phase)
    if result.thought != last:
        emit_thought(...)                 # «видно, что они думают»
    for msg in result.messages:
        if gated and novelty < min: drop
        else: write_message + событие
    sleep(POLL_INTERVAL)
```

Роли **идемпотентны относительно доски**: `step()` сначала смотрит, что уже
опубликовано, и только потом действует. Поэтому опрос в цикле никогда не
дублирует ни сообщение, ни команду роботу. Это важнее, чем кажется: без этого
любой перезапуск агента приводит к повторному выезду ровера.

## SOUL.md — личность агента

YAML-фронтматтер (читает машина) + тело (уходит агенту как системный промпт):

```markdown
---
id: drone-2
name: Magpie
role: scout               # scout | painter | coordinator | rover | safety_drone
capabilities: [move, photograph, detect_obstacle]
vote_weight: 1.0
priorities: [blindspot_curbs, coverage_completeness]
---

Ты — Magpie, дрон-разведчик. Ты предпочитаешь полное покрытие краёв скорости…
Пиши только если добавляешь то, чего на доске ещё нет.
```

`capabilities` — контракт, по которому координатор строит назначения.
`priorities` — тайбрейкеры при голосовании; разные приоритеты у четырёх дронов
делают фазу согласования настоящим спором, а не штампом. Последняя строка тела —
инструкция novelty gate.

## Контракт бриджа

Один и тот же для мока, Gazebo и железа:

```
POST /photograph      { sector }            -> { image_path, ts, sector }
POST /photograph      { cell:[x,y] }        -> { image_path, ts, cell }
POST /detect_obstacle { image_path }        -> { obstacles:[{type,xy,conf}], coverage }
POST /analyze         { cell, close_look }  -> { cargo, confidence, label }
POST /navigate        { from, to, grid }    -> ndjson: {pose,progress}… {status}
POST /move            { to:[x,y] }          -> { pose, ok }
POST /land / /takeoff {}                    -> { ok, landed, pose }
GET  /pose                                  -> { xy, heading }
GET  /healthz                               -> { ok: true }
```

Городской сценарий добавляет `/dwell {seconds, led}` (подтверждённая стоянка с
доказательством) и `/led`. Мост к реальному роверу добавляет `/stop`,
`/initial_pose`, `/config`, `/slam`, `/livemap`, `/map.png`, `/teleop`,
`/mapping`, `/goto`.

`/navigate` отдаёт **ndjson**: по кадру `{pose, progress}` на клетку, затем
финальный `{status}`. Клиент итерируется по потоку и эмитит событие `pose` на
кадр — дашборд рисует маршрут живьём.

Пока аппарат на земле (пауза, замена АКБ), мок отвечает **409** на
`/photograph`, `/move`, `/spray` — агент, проспавший паузу, получает явную
ошибку, а не тихо неверный результат.

**Почему бридж, а не инструменты внутри агента.** Логика робота меняется без
пересборки агента; тяжёлый ROS 2/камерный конвейер живёт только в бридже, а на
борту остаётся маленькая установка; наружу торчит короткий белый список
действий — **никакого generic shell или файлового инструмента**, поэтому
запутавшийся или отравленный промптом агент не может выйти за пределы «подвинуть
робота или вернуть снимок».

## Безопасность (из BUILD_BRIEF §11)

Формулировки, которые стоит перенести к себе в README архитектуры:

- контейнеры агентов — без доступа к хостовой оболочке, root-ФС только на
  чтение, кроме монтирования доски;
- внутренняя docker-сеть без выхода наружу, кроме эндпоинта модели и своего
  бриджа (`mesh` с `internal: true`);
- бридж валидирует каждый аргумент по строгой схеме на границе; координатор
  отбрасывает неверно сформированные сообщения, а не действует по ним;
- агенты потребляют внешний контент (снимки, реплики соседей) → инъекция
  промпта считается возможной по умолчанию;
- `navigate` ровера — единственное действие с последствиями в реальном мире:
  оно закрыто воротами `world.ready` и аппаратным стопом.
