## 5. Новая система: survey / поиск груза (реализована в этой сессии)

Полное описание — [survey.md](survey.md). Кратко: `TASK=survey`, четвёртый
таск на тех же примитивах. CHAT-переговоры о зонах (та же механика, что
scout_chat) → пошаговый облёт: **каждый ход дрона — JSON-план**
`[{fly_to,[x,y]},{wait,20},{photo_analyze}]` (LLM со схемой или
детерминированный фолбэк; валидатор клампит клетки/глаголы/тайминги) →
`FOUND` → **последовательная верификация остальными дронами** (кворум 2/3,
`VERIFY_ALL=1` — летят все по очереди; обратимый skip молчуна) → `world.ready`
+ `goal` → существующая роль rover едет к грузу. Closed-loop: после каждого
перелёта дрон берёт позицию из бриджа (`/pose`), а не из намерения — на
железе это телеметрия ROS2.

Новые файлы: `agent/roles/survey{,_scout,_common}.py`, `viz/survey.html`
(живой стенд: сетка, дроны, очередь верификации), `test_fixtures/survey-1/`,
`tests/test_survey.py`, `docs/survey.md`; расширены `bridge/mock.py`
(`/analyze`, фото клетки с синтезом PNG), `bridge_client.py`,
`drone/picoclaw_bridge_mcp.py` (tools `fly_to`/`photograph_cell`/`analyze`),
`Makefile` (`local-survey`, `demo-survey`), `run_local.sh`,
`docker-compose.yml` (TASK/WAIT_SCALE/SURVEY_*), `viz/server.py` (`/survey`).

**Баги, пойманные живыми прогонами в этой же сессии** (все исправлены):
1. *Гонка «находка в бэклоге против полного покрытия»* (mock): координатор
   отклонил обманку и в том же цикле объявил «поле покрыто, груз не найден»,
   не успев открыть очередь на уже лежащий на доске FOUND `[1,3]`. Фикс:
   продвижение бэклога в том же цикле + FAIL только при «покрыто ∧ нет
   кандидата ∧ нет бэклога ∧ все дроны отчитались».
2. *Кража клеток у живого соседа* (mock): быстрый дрон добирал клетки
   занятого верификацией соседа по отставшему world → двойные фото. Фикс:
   чужие клетки только при протухшем heartbeat владельца
   (`SURVEY_STALE_SEC`), покрытие берётся из progress всех дронов, не из
   world.
3. *Выброшенный поздний голос* (sverk): VERIFY дрона пришёл позже
   120-секундного leg-таймаута (медленный LLM-ход), координатор уже выкинул
   его из очереди, и фильтр по членству отбросил настоящий вердикт. Фикс:
   skip обратим, голос считается всегда; дефолты `VERIFY_LEG_SEC`/
   `SURVEY_STALE_SEC` подняты до 240 с (должны переживать медленный ход).

Это ровно тот класс багов, о котором предупреждал прошлый аудит: «каждый
консенсусный баг — real-brain-only» (№3) и «гонки живут на стыке
progress/messages» (№1–2). Правило «проверяй на живом мозге» подтверждается.

## 6. SOTA-предложения по агентной системе (приоритезированные)

Прошлогодний план адопции (audit-2026-07 §5) остаётся верным; ниже —
актуализация с учётом survey и текущего состояния области (структурные
выводы, verifier-ансамбли, event-sourcing, VLM, evals).

1. **Гигиена репозитория (P0, час работы).** Закоммитить всё рабочее дерево;
   дальше — мелкие коммиты + ветки. Добавить минимальный CI (GitHub Actions /
   Woodpecker): `python -m unittest discover -s tests` + mock-e2e smoke всех
   четырёх задач с проверкой `decision.result` (скрипт уже есть — регрессия
   этой сессии). Инцидент §2 показал цену: без docker-образа четырёхдневной
   давности painting был бы мёртв.
2. **Structured output до конца (P1).** Уже: чат/голоса/планы под
   `json_schema`. Осталось: большие compose-вызовы художников + `json_repair`
   вместо regex-слоя (план в HANDOFF-vllm-upgrade). Правило SOTA: сырой вывод
   LLM никогда не управляет исполнителем — в survey это уже так
   (`validate_plan` + детерминированный фолбэк); распространить на все таски.
3. **Верификация как переиспользуемый примитив (P1).** Последовательная
   кворумная перепроверка из survey (`FOUND → очередь → VERIFY → quorum_state`)
   — это общий паттерн «peer review перед принятием факта». Вынести в
   `roles/verify_common.py` и применять: к заявкам о покрытии секторов
   (street), к спорным ballot-кластерам (studio), к фактическим утверждениям
   дебатёров. Исследования консенсуса (Free-MAD, «Voting or Consensus?») —
   голосование независимых проверяющих устойчивее взаимного убеждения.
4. **Event-sourcing целиком (P1).** `events.jsonl` — источник истины,
   state-файлы — снапшоты с `last_applied_seq`, реплей после снапшота,
   чекпоинты на границах фаз в `runs/<id>/`. Даёт time-travel-отладку,
   идемпотентный рестарт и дешёвый аудит прогонов. (Прошлый аудит §5.5;
   LangGraph/MS-Agent-Framework validate дизайн.)
5. **Real-time вместо поллинга (P2).** Сейчас цикл — `sleep(1)`;
   `bb.wait_for_change()` уже написан и не используется. Перевод цикла на
   inotify/длинный poll хаба срежет латентность хода с ~1 с до мс — это и
   есть «closed loop, если скорость нейронок позволит»: на mock-мозге survey
   станет практически real-time, на LLM узким местом остаётся инференс
   (см. п.7).
6. **VLM-анализ фото (P2, разблокирует «настоящий» survey).** Сейчас анализ
   клетки — ground truth фикстуры (симуляция детектора). Шов уже правильный:
   `/analyze` на бридже. Подключить VLM (qwen2.5-VL на sverk-шлюзе или
   бортовой детектор) — и тот же протокол начнёт находить реальный груз на
   реальных снимках. Это же разблокирует canvas-grounded painting из прошлого
   аудита (§8b).
7. **Латентность инференса (P2).** Ходы survey на sverk занимают до минуты
   на дрона. Меры: короткие планы (уже), параллельные запросы дронов (уже —
   процессы независимы), спекулятивный следующий ход (планировать клетку N+1,
   пока летим к N), маленькая локальная модель для планов + большая для
   переговоров (роутинг по типу вызова — знакомый паттерн model-routing).
8. **Память между прогонами (P3).** `runs/<id>/` уже пишется. Добавить
   «уроки прогона» (что подтвердилось/отклонилось, тайминги фаз) в компактный
   `lessons.jsonl`, подмешиваемый координатору при INIT — дешёвая
   cross-run memory без внешних хранилищ.
9. **Наблюдаемость (P3).** В `llm.jsonl` есть parse-записи; добавить
   идентификатор прогона в каждое событие + сводку прогона (LLM-вызовы,
   ошибки, латентности по фазам) в конец `runs/<id>/summary.json` — сейчас её
   приходится собирать руками.
10. **Безопасность к продакшену (P3, до выхода из LAN).** `HUB_TOKEN`
    обязателен (сейчас опционален), rate-limit на POST хаба, server-side
    single-writer, e-stop в реальном бридже прежде `navigate`/`fly_to` (уже
    задокументировано в on-drone.md — довести до кода rclpy-узла).

Анти-рекомендация прошлого аудита остаётся в силе: **фреймворк не брать** —
все пункты выше по 30–150 строк на существующих примитивах.
