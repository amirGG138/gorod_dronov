# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это за репозиторий

Рабочая база для команды-участника инженерного соревнования **«Город дронов: социум ИИ агентов»** (очный этап 27–30 июля 2026). Кроме регламента и локальной выгрузки документации к аппаратам здесь уже есть свой код: симулятор города с диспетчером (`city/`), бортовой агент дрона (`onboard/`) и тестовый стенд полёта (`hold_aruco/`). Системы сборки и линтера по-прежнему нет — не изобретайте их. Тесты на `unittest` (pytest на этой машине **не установлен**): `python3 -m unittest discover -s tests`, 73 теста, проходят.

Вся справочная база лежит в **`docs/`** (навигатор — `docs/README.md`), код — в корне; `docs/` только для документации. Что лежит в корне:

- `city/` — симулятор поля и диспетчер, `onboard/drone_agent.py` — бортовая часть, `tests/` — тесты к ним. Порядок запуска — в `RUN.md`.
- `hold_aruco/` — отдельный тестовый стенд удержания дрона над ArUco-меткой, не часть зачётного решения (см. раздел ниже).
- `PLAN.md` — технический план, `PLAN-prostymi-slovami.md` — он же пересказом без жаргона.
- `sverh_snake/` — код с прошлого соревнования (см. ниже).

- `docs/reglament/` — **актуальный** регламент (редакция от 2026-07-27): `gorod_dronov_reglament.md` + исходный `Регламент_Город_дронов_Архипелаг_2026_1.pdf`, картинки поля в `images/`. `.md` получен из PDF, правьте его, а не PDF. Предыдущая редакция (с внутренней валютой и экономикой города) отменена — если где-то в репозитории всплывает «ставки», «рынок ресурсов», «дополнительные роверы в потоке», это устаревший текст.
- `docs/sverk/` — выгрузка https://edu.sverk.tech/documentation на 2026-07-24, 145 страниц.
- `docs/rover/` — выжимка по роверу из репозитория https://github.com/wodocanal/sverk_rover (HEAD `9a4e7cc`, выгружено 2026-07-27). Единственный источник по роверу: в `docs/sverk/` его нет.
- `docs/openclaw/` — разбор и снапшот https://github.com/StarumDDD/city_of_drones (HEAD `0a0b8592`, выгружено 2026-07-27), присланного организаторами как пример готовой части решения. Чужой проект, не документация; закрывает часть наших пробелов боевым опытом.
- `docs/field-map/` — ArUco-карта **нашего** полигона (`map.txt` в формате `aruco_map_node` + разбор в `docs/field-map/README.md`). Четыре маркера id 50/60/62/7, сторона 25 см, в клетках `[1,1] [4,1] [1,4] [4,4]`, шаг 2,4 м, начало координат в центре поля. Получена 2026-07-27, на железе не проверялась.

- `sverh_snake/` — рабочая папка **нашей же команды** с предыдущего соревнования («Змейка», зачёт 25.07.2026) на **том же железе** (Обрик ROS 2 + `sverk_interfaces`). Разбор «что берём» — в `docs/zmeyka.md`, читайте его вместо того, чтобы лезть в папку. Лежавшая там копия документации «Сверх» была побайтовым дубликатом `docs/sverk/` и удалена.

## Документация «Сверх»: как в ней ориентироваться

**Начинайте с `docs/sverk/README.md`.** Это не оглавление, а плотная выжимка по всем трём стекам: API, IP-адреса, пути `/dev` по платам, параметры АКБ, порядок настройки PX4 через QGC, известные дефекты документации. Почти на любой технический вопрос ответ уже там — читайте её раньше, чем грепать отдельные страницы.

Дальше: `docs/sverk/_INDEX.md` — постраничный список; `<каталог>/_ВСЁ.md` — весь раздел одним файлом (удобно грепать); `_raw/*.json` — сырые ответы API.

### Три независимых стека, и их легко перепутать

Это главная ловушка репозитория. Разделы описывают **разные несовместимые платформы**, но слаги и заголовки статей местами совпадают:

| Каталог | Платформа | API |
|---|---|---|
| `obrik-ros-2/` | Обрик на PX4 + ROS 2 Humble в Docker — **актуальная платформа** | `sverk_interfaces` |
| `mikrodron-whoop/` | Микродрон (Whoop), NPU + YOLO | `simple_offboard_py` |
| `obrik-ros-1-clover/` | Обрик на ROS Noetic + MAVROS — **legacy** | `rospy` + MAVROS |

Прежде чем давать код или совет, определитесь, о каком аппарате речь, и сверьтесь с соответствующим каталогом. Конкретные различия, о которые проще всего споткнуться:

- **Ось Z инвертирована.** В Обрике ROS 2 фрейм `body` — FLU, Z вверх: высота 1.5 м → `z=1.5`. В микродроне `Frame.BODY_NED`/`LOCAL_NED` — Z вниз: высота 0.7 м → `z=-0.7`.
- **Позиционирование в помещении разное.** Обрик ROS 2 — ArUco-поле на полу (камера вниз → `aruco_loc_node` → EKF2). Микродрон — оптический поток; в его `selfcheck` пункт `gps = FAIL` это норма.
- **Разные IP и порты.** Обрик ROS 2 — QGC по UDP:14550, SSH `sverk@<IP>` попадает **внутрь контейнера** `sverk_ros2` (порт 2222 — хост). Микродрон — фиксированный `10.10.1.1`, root/root. Clover — `192.168.11.1`, QGC по TCP:5760.
- В микродроне `navigate` требует ровно один из `yaw`/`yaw_rate`, иначе команда молча игнорируется.

Раздел «Замеченные проблемы в документации» в конце `docs/sverk/README.md` перечисляет места, где документация врёт или недописана (расходящиеся пути `/dev`, сломанные отступы в примере, отсутствующая ссылка на образ). Сверяйтесь с ним, прежде чем воспроизводить команду со страницы дословно.

### Чего в документации нет — не додумывайте

Три пробела `docs/sverk/`, критичных для соревнования. Два с половиной из них закрывает `docs/rover/`; всё, чего нет и там, — так и говорите, вместо того чтобы экстраполировать с дронов:

1. **Ровер** — в документации «Сверх» не упомянут вообще: ни API, ни IP, ни протокола. При этом по нему проходит основная часть баллов зачётной попытки. Закрыто выгрузкой `docs/rover/` (ROS 2 **Jazzy**, не Humble; свой пакет `rover_interfaces`).
2. **LLM/VLM и OpenClaw** — ни одного упоминания на 145 страницах, кроме ссылки на платформу в задании заочного этапа. Для ровера схема есть: `docs/rover/04-agent-mcp-i-llm.md` (OpenAI-совместимый endpoint + локальный MCP-сервер с whitelist инструментов). Для дронов закрыто `docs/openclaw/`: шлюз `https://ai.sverk.tech/v1` (OpenAI-совместимый, `SVERK_API_KEY`, модели `qwen35` и `gemma4-vlm`) плюс бортовой VLM на NPU через `ros2_mcp` (`:9092`, вызов `vlm_query`).
3. **Межагентная связь для ROS 2** — в документации описана только для legacy-стека Clover (`obrik-ros-1-clover/23-swarm.md`, ESP-NOW + `skyros`). Рабочий ROS 2-вариант есть в `docs/rover/05-fleet-mqtt-i-mezhagentnaya-svyaz.md` (MQTT, топики `fleet/v1/robots/<robot_id>/{command,answer,status,availability}`). В `docs/openclaw/` вместо MQTT — своя доска (общий том или HTTP-хаб).

Отдельно: у ровера есть **REST `rover_control_api v1` на `<ip>:8767`** с эксклюзивными лизами управления (`docs/openclaw/03-zhelezo-api-i-boevye-grabli.md`). Его нет ни в `docs/rover/`, ни в дереве апстрима `sverk_rover` — проверять на площадке в первый день.

## Ровер: как ориентироваться в `docs/rover/`

**Начинайте с `docs/rover/README.md`** — там же список известных расхождений апстримной документации. Дальше разделы `01`–`08` по темам. `_pdf-polnaya-dokumentaciya.md` — расшифровка официального PDF от 12.07.2026, он описывает **устаревшую** раскладку репозитория, доверять ему поверх разделов `01`–`08` нельзя.

Три ловушки, о которые проще всего споткнуться:

- **`/scan` ≠ то, что едет в Nav2.** Лидар публикует `/scan`, `rover_lidar_filter` вырезает корпус и выдаёт `/scan_filtered`; Nav2, SLAM, AMCL и агент работают с ним. В `topics.yaml` `scan_raw: /scan`, а `scan: /scan_filtered`.
- **Три топика скоростей.** `twist_mux` сводит в `/cmd_vel`: teleop (100) > `/cmd_vel_test` — туда пишет агент (75) > Nav2 (50). Писать напрямую в `/cmd_vel` — значит обойти мультиплексор.
- **Процента заряда нет.** Публикуется только `/battery_voltage` (`Float32`); объявленный `/battery/state` не пишет никто, а регламент требует ≥ 40 %.

Готовый формат логов у ровера уже есть: агент публикует JSON-конверты `{message_id, robot_id, status, text}` в `/agent/status` и `/agent/answer`. Под требование регламента о логах решений это дешевле принять как есть, чем изобретать своё.

## Чужое решение в `docs/openclaw/`

Присланный организаторами `StarumDDD/city_of_drones` — **не документация, а законченный проект другой команды** («OpenClaw stack»), доведённый до реального железа. Начинайте с `docs/openclaw/README.md`; исходники — в `docs/openclaw/snapshot/`.

Чем он ценен: `snapshot/agent/roles/city_world.py` и `city_executor.py` — регламент, переписанный в чистый детерминированный Python (энергия ровера, 3 с у башни / 5 с погрузки, уровень пожара = число циклов, эскорт ≤ 2 клеток, запрет проезда через непотушенный пожар); докстринги в `snapshot/bridge/sverk_flight.py` и `sverk_rover_bridge.py` — разбор граблей PX4 и Nav2, полученных на живых прогонах.

О чём помнить, прежде чем что-то оттуда переносить:

- **Лицензии нет**, а регламент запрещает обмен данными между командами. Факт рассылки организаторами стоит подтвердить; сдавать чужую архитектуру целиком — прямой способ потерять 20 баллов за креативность.
- **Треть репозитория мертва:** `payments/` (x402/AP2, EVM + TON, Solidity) написан под отменённую редакцию регламента с экономикой города. Сценарии «художники» и «дебаты» — тоже мимо задачи.
- **Что у них не сделано:** миссии города на живом ровере (проверены только на кубе в Gazebo), микродрон-ВУП (не подключён вообще), ROS 2-нода борта (`bridge/ros2/bridge_node.py`, сами помечают «на железе не гонялась ни разу»), Failsafe/KILL SWITCH как подсистема.
- Их калибровка поля (`snapshot/test_fixtures/city-1/map.json`: зарядка `[3,3]`, башня `[1,3]`, пады `[1,1] [4,1] [1,4] [4,4]`, ArUco DICT_4X4 id 51–54, маркер 29 см) — реконструкция по модели Domiki, а не официальная выдача. Клетки падов и шаг 2,4 м подтвердились нашей картой (`docs/field-map/`), а вот **id и размер маркера у них неверные**: у нас id 50, 60, 62, 7 и сторона 25 см. Остальное — рабочая гипотеза, проверяемая на площадке.

## Свой прошлый опыт в `sverh_snake/`

Наш же код с соревнования «Змейка» на **том же дроне** (Обрик ROS 2, `sverk_interfaces`). Разбор — **`docs/zmeyka.md`**, там же ссылки с номерами строк; в саму папку лезть обычно не нужно. Задача была другая (поле 7×7 сплошь в ArUco, поиск цветных «яблок», пролёт фигуры), а вот механика полёта переносится как есть и покрывает то, чего нет в `docs/sverk/`:

- камера публикует `yuv422_yuy2`, штатный `to_cv2` на нём падает — патч в `fly_head.py:173`. **На выданных бортах не подтвердилось:** там `bgr8`, патч не нужен (см. раздел `hold_aruco/`);
- `navigate(frame_id="body", z=0)` держит не высоту, а «сколько было в момент команды», ошибка копится только вверх; `yaw=0.0` там же означает «не менять курс», то есть закрепляет уже накопленный увод. Оба лечатся замером по метке (`hold_alt`, `hold_yaw`), без телеметрии;
- сторона метки для масштаба берётся как самое длинное ребро, а не среднее четырёх: наклонённый дрон иначе «считает» себя выше, чем он есть;
- `land()` может вернуть успех и ни к чему не привести — снижение подтверждается по растущей метке в кадре.

Два предупреждения при переносе: словарь там `DICT_4X4_50`, а маркеры нашего поля — id 50, 60, 62, 7 (`docs/field-map/`), и 60 с 62 в словарь на 50 элементов не влезают — нужен `DICT_4X4_1000`; и вся навигация построена на том, что метка видна почти всегда, чего на новом поле не будет.

Отдельно ценно как **сверка с `docs/openclaw/`**: два независимых решения на одном железе разошлись в способе летать — у нас `frame_id="body"` и полный отказ от `get_telemetry` (виснет без телеметрии FCU), у них `frame_id="map"` с телеметрией и keepalive. Таблица различий — в `docs/zmeyka.md`; какой путь рабочий на выданных бортах, проверять в первый день.

## `hold_aruco/` — тестовый стенд полёта и сверка с железом

`hold_aruco/hold_aruco.py` (~660 строк, один исполняемый файл) — взлёт, удержание над ближайшей видимой ArUco-меткой, посадка. **Не часть зачётного решения:** ни миссий, ни карты поля, ни роя, ни LLM. Это стенд, чтобы за один полёт в первый день проверить всё спорное про железо. Подробности, порядок первого прогона и таблица настроек — в `hold_aruco/README.md`, читайте его вместо файла.

Ядро перенесено из `sverh_snake/Archipelago2026/fly_head.py`, поэтому механика полёта та же: `frame_id="body"`, полный отказ от `get_telemetry`, замер высоты и курса по самой метке (`hold_alt`/`hold_yaw`), масштаб по самому длинному ребру. Отличия: словарь `DICT_4X4_1000` (в `4X4_50` не влезают наши id 60 и 62; тот же словарь стоит у бортовой `aruco_detect_node`, `dictionary_id=3`), фильтра по ID нет вовсе, мёртвая зона задана в метрах (`TOL_M = 0.10`), а не в долях кадра.

**Сверено на живом борте** `192.168.1.105` 2026-07-27 (без взлёта: selfcheck, один кадр, детектор на синтетике). Это отменяет часть утверждений, унаследованных из «Змейки» и повторённых выше в этом файле:

- камера отдаёт **`bgr8` 1280×960, 30 FPS**, а не `yuv422_yuy2` — патч `to_cv2` не нужен, но оставлен как безвредная страховка под другую сборку;
- OpenCV на борту **4.5.4**, `cv2.aruco.ArucoDetector` отсутствует — работает запасная ветка `cv2.aruco.detectMarkers(...)`;
- топики ArUco — **как в OpenClaw** (`/aruco/det/markers`, `/aruco/loc/pose_cov`, `/aruco/world_pose`), а не как в документации «Сверх»;
- наша карта поля на борт **залита** (`map_markers: received (4 markers)`);
- параметра `auto_release` у `offboard_control` на этой сборке **нет вовсе** — удержание позиции целиком наша задача;
- `selfcheck` требует вручную поднятой ноды `self_check_node` (в автозапуске её нет), исполняемый файл называется `selfcheck`, не `selfcheck.py`.

Непроверенным осталось то, для чего дрон должен стоять над полем: `MARKER_M` (0.25 — гипотеза из `docs/field-map/`, **перемерить рулеткой**), знак оси Y, реальная детекция метки в кадре.

Ещё две вещи, которые стоит знать про борт: `import cv2` там падает с `numpy.core.multiarray failed to import`, потому что поверх системного numpy 1.21.5 доставлен numpy 2.2.6, а `python3-opencv` 4.5.4 собран под 1.x — ломается весь Python-API платформы, включая `sverk_interfaces`; обход — отдельное окружение `~/venv_fly` (`python3 -m venv --system-site-packages`, затем `pip install "numpy<2"`). И для Failsafe/KILL SWITCH на борту уже есть готовые сервисы `/fmu_control/kill_switch`, `/emergency_stop`, `/fmu_control/force_disarm`, `/return_to_launch` — обвязывать надо их, а не изобретать своё.

## Ограничения регламента, связывающие любой код

Всё, что здесь будет написано, должно укладываться в: аппарат ≤ 0,5×0,5 м, потолок полёта 4 м, полётная зона — куб ≥ 8×8×4 м, заряд ≥ 40 % перед попыткой, обязательный Failsafe и работающий KILL SWITCH, полная автономность (ручное вмешательство штрафуется), запрет обмена данными между командами. Зачётная попытка — до 15 минут. Регламент требует `README.md` с описанием архитектуры агентной системы, LLM/VLM-компонентов, логики выбора миссий и маршрутов и **формата логов решений**; логи отдельным пунктом уже не оплачиваются, но без них нечем закрыть 30 баллов техзащиты за «использование LLM/VLM и принятие решений агентами», так что формат логирования держите в голове с самого начала.

Конкретика зачётной попытки (детали и оговорки — в `docs/reglament/gorod_dronov_reglament.md`):

- **Поле** — 6×6 клеток по 80×80 см (4,8×4,8 м) внутри полётной зоны. Четыре цветных района по углам, в центре стартовая зона = игровая станция зарядки, рядом клетка водонапорной башни, на крышах домов четыре площадки с ArUco под дроны-мониторы.
- **Состав:** агент-диспетчер (пишут участники) + 4 дрона-монитора («Сверх.Рой», ROS 2, NPU) + командный ровер + микродрон-ВУП. Диспетчер собирает картинки с мониторов и рассылает команды исполнителям.
- **Игровой заряд ровера ≠ реальный АКБ.** На старте 0 единиц; 1 секунда стоянки в зоне зарядки = 1 перемещение в соседнюю клетку; на нуле движение блокируется. Считать бюджет перемещений — задача диспетчера.
- **Миссия «Пожар»:** число на маркере = сколько раз съездить за водой к башне; на клетке башни ровно 3 с стоянки с мигающей лентой (пропуск аннулирует забор воды); ВУП параллельно ищет человека в окне горящего здания и отдаёт детекцию диспетчеру.
- **Миссия «Доставка»:** ровно 5 с стоянки со светодиодом на старте, затем маршрут к финишу; ВУП летит строго сзади не дальше двух клеток, мигалка ровера включена всю миссию. Пока «Пожар» не потушен, ехать через горящую клетку нельзя.
- **Оценка:** 150 баллов = до 100 за попытку + 50 за техзащиту (30 — LLM/VLM и принятие решений, 20 — креативность). Разбалловку самой попытки выдают только в первый день на площадке.

## Операции с файлами репозитория

**Обновить выгрузку документации** — процедура в разделе «Как обновить выгрузку» в `docs/sverk/README.md`. Кратко: сайт — Next.js SPA, `curl`/WebFetch отдают пустую оболочку, контент берётся из REST API без авторизации по слагам `obrik-ros-2`, `whoop`, `clover-2` (в общий листинг `/api/courses` они не попадают). Из Python — через `subprocess` + `curl`: `urllib` на этой машине падает с `SSL: CERTIFICATE_VERIFY_FAILED`.

**Обновить выгрузку по роверу** — процедура в конце `docs/rover/README.md`. Кратко: `git clone` репозитория `sverk_rover` здесь отваливается по таймауту (58 МБ), берите дерево через GitHub API и файлы по одному через `raw.githubusercontent.com`; больше ~10 параллельных `curl` дают `Connection reset by peer`.

**Перегенерировать `.md` из PDF.** На этой машине **нет** `poppler`/`pdftotext`/`pdftoppm` и нет `brew`, поэтому встроенное чтение PDF и `Read` по PDF не работают. Рабочий путь — временный venv в scratchpad:

```bash
python3 -m venv venv && ./venv/bin/pip install pypdf
./venv/bin/python -c "
from pypdf import PdfReader
r = PdfReader('docs/reglament/Регламент_Город_дронов_Архипелаг_2026_1.pdf')
print('\n'.join(p.extract_text() or '' for p in r.pages))
"
```

Извлечённый текст содержит артефакты вёрстки — разрывы внутри слов (`Сист ема`, `количест во`) и дефисы вместо тире. При правке `.md` их нужно вычищать; текущая версия файла уже вычищена.
